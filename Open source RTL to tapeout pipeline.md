# Open tools carry RTL to tapeout, step by step

The entire open-source path from Verilog to a fab-ready GDS on SkyWater sky130 is, in October 2026, one program: **LibreLane 3.0.16** (the renamed OpenLane 2, maintained by the FOSSi Foundation after Efabless closed) drives Verilator for lint, Yosys 0.62 plus ABC for synthesis, OpenROAD for floorplan, placement, clock tree, routing, parasitic extraction and IR drop, OpenSTA for nine-corner timing, Magic 8.3.623 and KLayout 0.30.7 for GDS stream-out and two independent DRC decks, and Netgen 1.5.316 for LVS, in a fixed **80-step "Classic" flow** whose every step is gated by a `RUN_*` switch and checked by a `Checker.*` step ([LibreLane classic.py](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py); [Changelog 3.0.0](https://github.com/librelane/librelane/blob/main/Changelog.md)). You install it natively on Apple Silicon or Linux with one Nix command and `nix-shell`, fetch the pinned sky130 PDK (`open_pdks` commit `8afc8346…`) through `ciel`, and a four-key `config.json` (`DESIGN_NAME`, `VERILOG_FILES`, `CLOCK_PORT`, `CLOCK_PERIOD`) is enough to produce a GDS, a powered gate-level netlist, per-corner SDF/SPEF/LIB and a flat `final/metrics.json` ([LibreLane macOS install](https://librelane.readthedocs.io/en/latest/installation/nix_installation/installation_macos.html); [Newcomers' Tutorial](https://librelane.readthedocs.io/en/latest/getting_started/newcomers/index.html)). The tool makes most micro-decisions automatically (ideal clocks before CTS, 20 %/10 % slew margins, setup-then-hold repair with 0.05/0.1 ns and 0.025/0.05 ns margins, 50 % buffer caps, 0.3 global-routing capacity derate, 64 detailed-routing iterations), but a handful of judgments remain yours: the real clock period and I/O timing, which paths are false or multicycle, which of the nine sky130 corners constitute sign-off, how much area to spend on utilization and buffers, when hold fixing is eating setup, and when to go back to RTL and pipeline ([OpenLane 2 timing closure guide](https://openlane2.readthedocs.io/en/dev/usage/timing_closure/index.html); [LibreLane openroad.py](https://github.com/librelane/librelane/blob/main/librelane/steps/openroad.py)). Tiny Tapeout fixes the floorplan for you (a 1×1 sky130 tile is **161.00 × 111.52 µm**, pins come from a template DEF, `met5` is forbidden, the clock is 20 ns and the pad limit is 66 MHz), runs LibreLane 3.0.14 in GitHub Actions, and the open sky130 shuttle **TTSKY26d closes 2026-11-30** ([tile_sizes.yaml](https://github.com/TinyTapeout/tt-support-tools/blob/main/tech/sky130A/tile_sizes.yaml); [Tiny Tapeout chips page](https://tinytapeout.com/chips/)). Every stage up to and including precheck is scriptable, so a Claude Code agent run with `--permission-mode dontAsk --permission-prompts none` behind immutable tests and a Makefile gate ladder can lint, simulate, synthesize, harden, gate-level simulate and precheck overnight; what it cannot do is decide the spec, pay for the tile, click "Submit a new revision", or explain an LVS/DRC failure it does not understand, and those are the items it should queue for you in the morning ([Claude Code headless docs](https://code.claude.com/docs/en/headless); [tt_tool.py](https://github.com/TinyTapeout/tt-support-tools/blob/main/tt_tool.py)).

## LibreLane 3.0.16 is the flow; install it natively with Nix

The naming confusion is worth settling first because every tutorial you will find uses a different name for the same code. OpenLane 1 is the Tcl-based flow that did hundreds of tapeouts; the LibreLane FAQ says it "is in maintenance mode, but is not recommended at all for new designs." OpenLane 2 was a ground-up Python rewrite started at Efabless in 2022 and soft-launched in February 2024; when Efabless shut down in March 2025 its authors forked it under the FOSSi Foundation as **LibreLane**, with 2.4.0 as the first LibreLane release (July 2025) and **3.0.0 on 2026-03-25** as the first major version outside Efabless ([FOSSi announcement](https://fossi-foundation.org/blog/2025-08-17-librelane); [LibreLane 3.0 post](https://fossi-foundation.org/librelane/blog/2026-03-25-website_release_3-0)). The PyPI `openlane` package froze at 2.3.10 in February 2025 and the `efabless/openlane2` README now redirects to `librelane/librelane` ([PyPI openlane](https://pypi.org/project/openlane/); [efabless/openlane2](https://github.com/efabless/openlane2)). LibreLane has been "used for all Tiny Tapeout shuttles since 3.5," and the Python module is simply `librelane` (so any OpenLane 2 example maps by replacing `openlane` with `librelane` and applying the 3.0 variable renames discussed later) ([LibreLane FAQ](https://librelane.readthedocs.io/en/latest/faq.html)). OpenROAD-flow-scripts (ORFS) is the OpenROAD Project's own Make/Tcl flow; it supports the same PDKs plus ASAP7 and Nangate45 and ships `.deb` binaries, but it is monolithic and Tcl-configured, whereas LibreLane is plugin-based with JSON/YAML/Tcl/Python configs, type-checked variables and bundled dependencies ([LibreLane FAQ](https://librelane.readthedocs.io/en/latest/faq.html)). For an agent-driven pipeline LibreLane is the right choice because its Python API returns a `State` object and writes machine-readable `state_out.json` after every step.

The tool versions you will actually run inside LibreLane 3.0.x are pinned by its Nix environment (nix-eda 6.11.0 on nixpkgs nixos-25.11): **KLayout 0.30.7, Magic 8.3.623, Netgen 1.5.316, Yosys 0.62 with the yosys-slang frontend replacing Synlig, Verilator 5.044, OpenROAD commit `dcf36133`, a patched OpenSTA `857316ff`**, and Python 3.12 ([Changelog 3.0.0](https://github.com/librelane/librelane/blob/main/Changelog.md)). Outside LibreLane the front-end tools have moved further: Yosys is at v0.68 on GitHub (05 Aug 2026) and 0.70 in Homebrew, with sv-elab (formerly yosys-slang) integrated since v0.67 for full SystemVerilog; Verilator 5.052 (2026-09-05); Icarus Verilog 13.0 (the first stable v13, with a changed `vvp` file format); cocotb 2.1.0 (2026-08-30, Python ≥3.9); the OSS CAD Suite nightly of 2026-09-13; Surfer 0.7.0 ([Yosys releases](https://github.com/YosysHQ/yosys/releases); [brew yosys](https://formulae.brew.sh/api/formula/yosys.json); [Verilator Changes](https://github.com/verilator/verilator/blob/master/Changes); [iverilog releases](https://github.com/steveicarus/iverilog/releases); [PyPI cocotb](https://pypi.org/pypi/cocotb/json); [oss-cad-suite releases](https://github.com/YosysHQ/oss-cad-suite-build/releases)). You will run two tool sets side by side: the LibreLane Nix shell for the back end and a newer front-end set (OSS CAD Suite or Homebrew) for simulation and formal.

The recommended install on both Apple Silicon macOS and Linux is Nix. Requirements on macOS are a minimum of macOS 15 (Sequoia), 8 GiB RAM, with M1 or later and 16 GiB recommended; **LibreLane's first 2027 release will drop Intel Macs**. On Linux the docs say Ubuntu 22.04+ is the primary target, quad-core 2.0 GHz and 8 GiB minimum, and warn not to install Nix from apt ([macOS Nix install](https://librelane.readthedocs.io/en/latest/installation/nix_installation/installation_macos.html); [Linux Nix install](https://librelane.readthedocs.io/en/latest/installation/nix_installation/installation_linux.html)). The commands are identical on both platforms:

```sh
# Step 1: Nix with the FOSSi binary cache (~5 min; close all terminals afterwards)
curl --proto '=https' --tlsv1.2 -fsSL https://artifacts.nixos.org/nix-installer | sh -s -- install --no-confirm --extra-conf "
    extra-substituters = https://nix-cache.fossi-foundation.org
    extra-trusted-public-keys = nix-cache.fossi-foundation.org:3+K59iFwXqKsL7BNu6Guy0v+uTlwsxYQxjspXzqLYQs=
    extra-experimental-features = nix-command flakes
"
# If Nix is already installed: add those three lines to /etc/nix/nix.conf, then: sudo pkill nix-daemon
# Step 2–4
git clone https://github.com/librelane/librelane
cd librelane && nix-shell          # first run ~10 min, ~3 GiB from the cache
librelane --smoke-test             # also fetches sky130A into ~/.ciel via Ciel
```

The smoke test variant `librelane --log-level ERROR --condensed --show-progress-bar --smoke-test` is quieter, and `librelane --run-example spm` from a fresh directory runs the bundled serial-parallel multiplier ([Newcomers' Tutorial](https://librelane.readthedocs.io/en/latest/getting_started/newcomers/index.html); [docs _running_example.md](https://github.com/librelane/librelane/blob/main/docs/source/installation/nix_installation/_running_example.md)). The FAQ explains why Nix rather than Docker: it "doesn't add a virtualization penalty on macOS, and does not require the entire image to be re-downloaded every time an update occurs," and `aarch64-darwin` has been a first-class target since the OpenLane 2.0 era, with KLayout Mach-O binaries patched to find their dylibs, Magic built with cairo so its GUI works on macOS, and an OpenROAD GUI crash on non-libstdc++ platforms fixed in 2.3.9 ([LibreLane FAQ](https://librelane.readthedocs.io/en/latest/faq.html); [Changelog](https://github.com/librelane/librelane/blob/main/Changelog.md)). The one known gap on ARM and macOS is VHDL: the yosys-ghdl plugin is excluded from ARM and macOS builds ("never worked"), so the `VHDLClassic` flow is effectively Linux-x86 only ([Changelog](https://github.com/librelane/librelane/blob/main/Changelog.md)).

The Docker route is `brew install make python python-tk && brew install --cask docker` (share `/Users` under Docker Desktop → Resources → File Sharing), then `python3 -m pip install librelane` and `python3 -m librelane --dockerized --smoke-test`; `--dockerized` with no further arguments drops you into a shell in the `ghcr.io/librelane/librelane:<version>` image with your home and PDK root mounted, and the flag "must precede all options except --docker-mount" ([Docker macOS](https://github.com/librelane/librelane/blob/main/docs/source/installation/docker_installation/installation_macos.md); [docker _common.md](https://github.com/librelane/librelane/blob/main/docs/source/installation/docker_installation/_common.md); [cli.py](https://github.com/librelane/librelane/blob/main/librelane/flows/cli.py)). A pip-only install (`python3 -m pip install --upgrade librelane`, Python ≥3.10 with Tkinter) is labelled "advanced, not recommended… at your own risk" because you must supply your own OpenROAD/Magic/KLayout/Netgen binaries; Tiny Tapeout uses exactly this pip install plus Docker ([README](https://github.com/librelane/librelane); [TT local hardening](https://www.tinytapeout.com/guides/local-hardening)).

The PDK is managed by **Ciel** (`python3 -m pip install --user --upgrade --no-cache-dir ciel`; LibreLane 3.0.16 pins `ciel>=2.3.1,<3` and calls `ciel.fetch()` automatically unless you pass `--manual-pdk`). Versions for sky130 are open_pdks commit hashes, and the hash LibreLane 3.0.16 pins is **`sky130: 8afc8346a57fe1ab7934ba5a6056ea8b43078e71`**, which is the same hash Tiny Tapeout's docs use in their `ciel enable` example; commands are `ciel ls-remote --pdk-family sky130`, `ciel ls --pdk-family sky130`, `ciel enable --pdk-family sky130 <hash>` ([PyPI ciel](https://pypi.org/project/ciel/); [pdk_hashes.yaml](https://github.com/librelane/librelane/blob/main/librelane/pdk_hashes.yaml); [pyproject.toml](https://github.com/librelane/librelane/blob/main/pyproject.toml)). PDK root resolves as `--pdk-root` flag → `PDK_ROOT` env → `~/.ciel`; the PDK variant resolves as config `PDK` → `--pdk` → `PDK` env → `sky130A`. **sky130A** is five metal layers plus local interconnect with "better-calibrated timing extraction"; sky130B adds a ReRAM layer between met1 and met2 that doubles via1 height and changes timing. The default standard-cell library is `sky130_fd_sc_hd` and the PDK's flow config lives at `$PDK_ROOT/sky130A/libs.tech/librelane/config.tcl` and `.../librelane/sky130_fd_sc_hd/config.tcl` ([About PDKs](https://librelane.readthedocs.io/en/latest/usage/about_pdks.html)). The sky130 simulation models that the gate-level testbench needs are at `$PDK_ROOT/sky130A/libs.ref/sky130_fd_sc_hd/verilog/primitives.v` and `sky130_fd_sc_hd.v` ([tt template Makefile](https://github.com/TinyTapeout/tt10-verilog-template/blob/main/test/Makefile)).

For the front end, the OSS CAD Suite gives you everything in one tarball on `linux-x64`, `linux-arm64`, `darwin-arm64` (macOS 13+; Intel-mac builds "are being phased out") and `windows-x64`: Yosys with the slang plugin, sby/eqy/mcy with Boolector, Yices 2, Z3, Bitwuzla, rIC3 and avy (super_prove is linux-x64 only), Verilator, Icarus, cocotb, GTKWave and Surfer. Extract it, on macOS run `xattr -d com.apple.quarantine` on the archive or `./activate` once, then `source oss-cad-suite/environment` ([oss-cad-suite-build README](https://github.com/YosysHQ/oss-cad-suite-build)). The Homebrew alternative has native arm64 bottles for `yosys` 0.70, `verilator` 5.052, `icarus-verilog` 13.0 and `surfer` 0.7.0, so `brew install yosys verilator icarus-verilog surfer` plus `pip install cocotb pytest cocotb-coverage` is a complete native front end ([brew yosys](https://formulae.brew.sh/api/formula/yosys.json); [brew verilator](https://formulae.brew.sh/api/formula/verilator.json); [brew icarus-verilog](https://formulae.brew.sh/api/formula/icarus-verilog.json); [brew surfer](https://formulae.brew.sh/formula/surfer)). On Ubuntu the Tiny Tapeout docs' `sudo apt install iverilog verilator` and `pip3 install cocotb pytest` work but lag in version ([Tiny Tapeout testing](https://tinytapeout.com/hdl/testing/)). For SymbiYosys from source you need Yosys (which includes `yosys-smtbmc` and `yosys-abc`), sby itself, `pip install click`, Boolector with btor2tools, Yices 2, and optionally Z3/super_prove/Avy/rIC3 1.5.2, which is why the install page recommends the OSS CAD Suite ([sby install](https://yosyshq.readthedocs.io/projects/sby/en/latest/install.html)).

## The 80-step Classic flow and every file that moves between tools

The Classic flow is a `SequentialFlow` of 80 step entries, several of them repeated (`OpenROAD.STAMidPNR` four times, `OpenROAD.CheckAntennas` twice), each writing to a numbered directory `runs/<tag>/NN-<tool>-<step>/` that contains `COMMANDS` (the exact commands run), `config.json` (every variable visible to that step), `state_in.json` and `state_out.json` (the dictionary of design views plus accumulated metrics), the step log, `*.process_stats.json`, and whatever views it produced ([LibreLane classic.py](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py); [Newcomers' Tutorial](https://librelane.readthedocs.io/en/latest/getting_started/newcomers/index.html)). Read in sequence, the flow is six phases. Phase one is lint and synthesis: `Verilator.Lint` → three lint checkers → `Yosys.JsonHeader` → `Yosys.Synthesis` → `Checker.YosysUnmappedCells`, `Checker.YosysSynthChecks`, `Checker.NetlistAssignStatements` → `OpenROAD.CheckSDCFiles` → `OpenROAD.CheckMacroInstances` → `OpenROAD.STAPrePNR`. Phase two is floorplanning: `OpenROAD.Floorplan` → `OpenROAD.DumpRCValues` → `Odb.CheckMacroAntennaProperties` → `Odb.SetPowerConnections` → `Odb.ManualMacroPlacement` → `OpenROAD.CutRows` → `OpenROAD.TapEndcapInsertion` → `Odb.AddPDNObstructions` → `OpenROAD.GeneratePDN` → `Odb.RemovePDNObstructions` → `Odb.AddRoutingObstructions` → `OpenROAD.GlobalPlacementSkipIO` → `OpenROAD.IOPlacement` → `Odb.CustomIOPlacement` → `Odb.ApplyDEFTemplate`. Phase three is placement and clocking: `OpenROAD.GlobalPlacement` → `Odb.WriteVerilogHeader` → `Checker.PowerGridViolations` → `STAMidPNR` → `OpenROAD.RepairDesignPostGPL` → `Odb.ManualGlobalPlacement` → `OpenROAD.DetailedPlacement` → `OpenROAD.CTS` → `STAMidPNR` → `OpenROAD.ResizerTimingPostCTS` → `STAMidPNR`. Phase four is routing: `OpenROAD.GlobalRouting` → `OpenROAD.CheckAntennas` → `OpenROAD.RepairDesignPostGRT` (off by default) → `Odb.DiodesOnPorts` → `Odb.HeuristicDiodeInsertion` (off) → `OpenROAD.RepairAntennas` → `OpenROAD.ResizerTimingPostGRT` (off) → `STAMidPNR` → `OpenROAD.DetailedRouting` → `Odb.RemoveRoutingObstructions` → `CheckAntennas` → `Checker.TrDRC` → `Odb.ReportDisconnectedPins` + checker → `Odb.ReportWireLength` + checker → `OpenROAD.FillInsertion` → `Odb.CellFrequencyTables`. Phase five is signoff analysis: `OpenROAD.RCX` → `OpenROAD.STAPostPNR` → `OpenROAD.IRDropReport`. Phase six is physical signoff: `Magic.StreamOut` → `KLayout.StreamOut` → `KLayout.Render` → `Magic.WriteLEF` → `Odb.CheckDesignAntennaProperties` → `KLayout.XOR` + checker → `Magic.DRC` → `KLayout.DRC` → two DRC checkers → `Magic.SpiceExtraction` → `Checker.IllegalOverlap` → `Netgen.LVS` → `Checker.LVS` → `Yosys.EQY` (off) → `Checker.SetupViolations`, `HoldViolations`, `MaxSlewViolations`, `MaxCapViolations` → `Misc.ReportManufacturability` ([LibreLane classic.py](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py); [Flows reference](https://librelane.readthedocs.io/en/latest/reference/flows.html)).

The checkers have two failure modes that matter for automation. `NetlistAssignStatements`, `YosysUnmappedCells`, the lint checkers and `DisconnectedPins` raise an immediate `StepError`; DRC, LVS, XOR, long-wire, timing, slew, cap, illegal-overlap and PDN violations raise a *deferred* error that is collected and reported at the end as a `StepException` after the rest of the flow completes, so a run with a hold violation still produces a GDS you can inspect. A checker whose threshold variable is unset is skipped with a warning, and a missing metric produces "Are you sure the relevant step was run?" ([checker.py](https://github.com/librelane/librelane/blob/main/librelane/steps/checker.py); [Writing Custom Flows](https://librelane.readthedocs.io/en/latest/usage/writing_custom_flows.html)). OpenROAD steps parse `[ERROR CODE-NNNN]` lines into step errors, silently ignoring exactly three codes: `ORD-0039` (".openroad ignored with -python"), `ODB-0220` (obsolete `NOWIREEXTENSIONATPIN` in LEF) and `STA-1256` ("table template not found") ([LibreLane openroad.py](https://github.com/librelane/librelane/blob/main/librelane/steps/openroad.py)).

What moves between tools is a small set of formats, and knowing which step produces each is what lets you run the flow by hand. RTL enters as `.v`/`.sv` (`VERILOG_FILES`) with `.vh` includes; Yosys reads the standard-cell Liberty files with `read_liberty -lib -ignore_miss_dir -setattr blackbox` purely as black boxes (gzipped SCL `.lib` is not supported for synthesis) and ABC reads the same Liberty for timing-driven mapping, with constraints passed as a two-line `synthesis.abc.sdc` containing only `set_driving_cell` and `set_load` because "ABC only supports these two" ([openlane2 ys_common.py](https://github.com/efabless/openlane2/blob/main/openlane/scripts/pyosys/ys_common.py); [openlane2 synthesize.py](https://github.com/efabless/openlane2/blob/main/openlane/scripts/pyosys/synthesize.py)). Synthesis emits `<design>.nl.v` (written with `write_verilog -noattr -noexpr -nohex -nodec -defparam`) and `<design>.nl.v.json` from `write_json`, plus `reports/{latch,pre_synth_chk,pre_techmap,post_dff,chk,stat}.rpt` and `stat.json` whose `design.num_cells`, `design.area` and `num_cells_by_type` feed the metrics `design__instance__count`, `design__instance__area` and `design__instance_unmapped__count` (any cell type starting with `$`) ([openlane2 steps/pyosys.py](https://github.com/efabless/openlane2/blob/main/openlane/steps/pyosys.py)). The SDC is either LibreLane's `scripts/base.sdc` (via `FALLBACK_SDC`) or your `PNR_SDC_FILE`/`SIGNOFF_SDC_FILE`. Floorplan turns the netlist into an OpenDB `.odb` database and a `.def`, re-emitting `.nl.v` (unpowered) and `.pnl.v` (powered, with `VPWR`/`VGND`) at every OpenROAD step; the technology and cell `.lef` files come from the PDK (`TECH_LEFS`, `CELL_LEFS`). RCX writes one `.spef` per interconnect corner (`nom`/`min`/`max`); STA writes one `.sdf` and one `.lib` per corner. Magic and KLayout each stream `.def` to `.gds` (and `mag`/`mag_gds`), Magic writes the abstract `.lef`, Magic's extractor writes `.spice`, and Netgen compares that SPICE to the `.pnl.v` ([design_format.py](https://github.com/librelane/librelane/blob/main/librelane/state/design_format.py); [Newcomers' Tutorial](https://librelane.readthedocs.io/en/latest/getting_started/newcomers/index.html)). The full list of design-format IDs in 3.0.16 is `nl` (`.nl.v`), `logical_nl`, `pnl` (`.pnl.v`), `sdf_pnl` (no fill cells), `logical_pnl`, `def`, `lef`, `sdc`, `sdf` (per corner), `spef` (nom/min/max), `lib` (per corner), `spice`, `cdl`, `gds`, `vh`, `spice_rcx`, `render` (`.png`), `klayout_gds`, `mag`, `mag_gds`, `json_h` ([design_format.py](https://github.com/librelane/librelane/blob/main/librelane/state/design_format.py)).

At the end, `runs/<tag>/final/` holds one subfolder per format (`def gds json_h klayout_gds lef lib mag mag_gds nl odb pnl sdc sdf spef spice vh render`) plus `metrics.csv` and `metrics.json`; the run root has `resolved.json` (the fully resolved config), `flow.log`, `error.log`, `warning.log`, `info.log` and `tmp/`. The STA directory is the one you will read most: `NN-openroad-stapostpnr/summary.rpt` is a table with columns Corner/Group, Hold Worst Slack, Reg-to-Reg, Hold TNS, Hold Vio Count, Setup Worst Slack, Setup TNS, Setup Vio Count, Max Cap Violations, Max Slew Violations, with one row per corner and an "Overall" row; each `<corner>/` subdirectory has `checks.rpt`, `max.rpt` (setup paths), `min.rpt` (hold paths), `skew.max/min.rpt`, `tns/wns/ws.max/min.rpt`, `violator_list.rpt`, `power.rpt`, `clock.rpt`, `unpropagated.rpt`, the per-corner `.lib` and `.sdf`, and `sta.log` ([Newcomers' Tutorial](https://librelane.readthedocs.io/en/latest/getting_started/newcomers/index.html); [openlane2 corner.tcl](https://github.com/efabless/openlane2/blob/main/openlane/scripts/openroad/sta/corner.tcl)). DRC markers land in `NN-magic-drc/reports/drc.klayout.xml` and `NN-klayout-drc/report/drc.lyrdb` (renamed from `.xml` in 3.0) and open in KLayout's Marker Browser; `netgen-lvs.log` must end with "Final result: Circuits match uniquely." and `lvs.netgen.rpt` shows layout-vs-schematic tables side by side ([Newcomers' Tutorial](https://librelane.readthedocs.io/en/latest/getting_started/newcomers/index.html); [Changelog 3.0.0](https://github.com/librelane/librelane/blob/main/Changelog.md)).

A config file is a flat key-value JSON, YAML or Tcl file in the design directory, with `pdk::<glob>` and `scl::<glob>` conditional blocks, `dir::` (shorthand for `refg::$DESIGN_DIR/`), `pdk_dir::`, `ref::$VAR`, `refg::` globs and `expr::` arithmetic such as `"PL_TARGET_DENSITY_PCT": "expr::($FP_CORE_UTIL + 10.0)"`; JSON must be pure ECMA-404 with no comments ([Configuration reference](https://librelane.readthedocs.io/en/latest/reference/configuration.html)). The minimal config from the tutorial is `{"DESIGN_NAME": "pm32", "VERILOG_FILES": ["dir::pm32.v", "dir::spm.v"], "CLOCK_PERIOD": 25, "CLOCK_PORT": "clk"}` ([Newcomers' Tutorial](https://librelane.readthedocs.io/en/latest/getting_started/newcomers/index.html)). A `meta` block selects the flow or substitutes steps: `{"meta": {"flow": "Classic", "substituting_steps": {"OpenROAD.STAMidPNR*": null, "Magic.DRC": "KLayout.DRC"}}}`, or `{"meta": {"version": 2, "flow": ["Yosys.Synthesis", ...]}}` to list steps outright ([Writing Custom Flows](https://librelane.readthedocs.io/en/latest/usage/writing_custom_flows.html)). The 3.0 renames you must know when reading older material: all `FP_IO_*` became `IO_PIN_*`, all `FP_PDN_*` became `PDN_*`, `PL_TIME_DRIVEN` → `PL_TIMING_DRIVEN`, `GRT_ANTENNA_ITERS/MARGIN` → `GRT_ANTENNA_REPAIR_ITERS/MARGIN`, `FILL_CELL`/`DECAP_CELL` → `FILL_CELLS`/`DECAP_CELLS`, `EXTRA_GDS_FILES` → `EXTRA_GDS`, `FALLBACK_SDC_FILE` → `FALLBACK_SDC`, `QUIT_ON_*` → `ERROR_ON_*`, `USE_SYNLIG` → `USE_SLANG`, `MAGIC_NO_EXT_UNIQUE` → `MAGIC_EXT_UNIQUE`, and `DRT_MIN/MAX_LAYER` were removed in favour of `RT_MIN/MAX_LAYER`. Deprecated names still work in config files but **not** in `-c KEY=VALUE` overrides, whose values must be valid JSON ([Changelog 3.0.0](https://github.com/librelane/librelane/blob/main/Changelog.md); [cli.py](https://github.com/librelane/librelane/blob/main/librelane/flows/cli.py)).

Running and resuming is the same from the CLI and from Python. The CLI is `librelane [--dockerized] [--flow X] [--run-tag T | --last-run] [--overwrite] [--from ID] [--to ID] [--only ID] [--skip ID] [-c KEY=VALUE] [-j N] config.json`, with `--with-initial-state FILE`, `--initial-state-element-override FORMAT=PATH`, `--save-views-to DIR`, `--reproducible ID` (bundle a step for a bug report) and `--smoke-test` ([cli.py](https://github.com/librelane/librelane/blob/main/librelane/flows/cli.py)). From Python, `from librelane.flows import Flow; Classic = Flow.factory.get("Classic"); flow = Classic(config_dict, design_dir="."); state = flow.start(tag="run1")`; `Flow.start(with_initial_state=None, tag=None, last_run=False, *, overwrite=False)` resumes from "the latest state_out.json (by filesystem modification date)" when `last_run=True`; a `SequentialFlow` subclass declares `Steps = [...]` and optional `Substitutions`; individual steps run as `Yosys.Synthesis(config=cfg, state_in=prev).start()`; `config.copy(FP_CORE_UTIL=9)` derives variants and `start_step_async()` returns a Future for parallel sweeps ([Writing Custom Flows](https://librelane.readthedocs.io/en/latest/usage/writing_custom_flows.html); [flow.py](https://github.com/librelane/librelane/blob/main/librelane/flows/flow.py)). A single step can also be run standalone as `python3 -m librelane.steps run --id <Step.ID> --config <config.json> --state-in <state_in.json> --output <dir>` ([steps/__main__.py](https://github.com/librelane/librelane/blob/main/librelane/steps/__main__.py)). To look at an intermediate result: `librelane --last-run --flow OpenInKLayout config.json --with-initial-state runs/<tag>/18-openroad-tapendcapinsertion/state_out.json`, or `--flow OpenInOpenROAD` (loads the ODB plus libs and SPEF) or `--flow OpenInMagic` ([Newcomers' Tutorial](https://librelane.readthedocs.io/en/latest/getting_started/newcomers/index.html); [Flows reference](https://librelane.readthedocs.io/en/latest/reference/flows.html)).

## Front end: write Verilog that survives `-noautowire`, lint it, test it twice

Yosys's native `read_verilog` supports "a large subset of Verilog-2005" and, with `-sv`, "only a small subset of SystemVerilog"; its own help text advises using a simulator such as Icarus to check syntax because the frontend "has not very good error reporting" ([Yosys verilog_frontend.cc](https://github.com/YosysHQ/yosys/blob/main/frontends/verilog/verilog_frontend.cc)). LibreLane reads every file with exactly `read_verilog -defer -noautowire -sv -I<dir> -D<define> <file>` and applies `SYNTH_PARAMETERS` with `chparam -set <param> <value> <top>`, adding the defines `PDK_<PDK>`, `SCL_<SCL>`, `__openlane__` and `__pnr__` ([openlane2 ys_common.py](https://github.com/efabless/openlane2/blob/main/openlane/scripts/pyosys/ys_common.py)). The `-noautowire` flag is the single most consequential detail for an RTL author: it makes the default net type `none`, so an undeclared identifier that Icarus happily auto-wired becomes a synthesis error. Put `` `default_nettype none `` at the top of every file so the simulator catches it first. For real SystemVerilog, Yosys v0.67 integrated **sv-elab** (formerly yosys-slang, built on the slang library, supporting the synthesizable subset of IEEE 1800-2017/2023 and tested on Ibex, OpenTitan, CV32E40P and Black Parrot); LibreLane exposes it as `USE_SLANG: true` with `SLANG_ARGUMENTS`, and warns that with slang you must pass `--keep-hierarchy` yourself if you want hierarchy preserved ([sv-elab README](https://github.com/povik/yosys-slang); [LibreLane pyosys.py](https://github.com/librelane/librelane/blob/main/librelane/steps/pyosys.py)). The other route is sv2v v0.0.13, which converts SV to Verilog-2005 and now turns `unique`/`priority` into `parallel_case`/`full_case` attributes ([sv2v releases](https://github.com/zachjs/sv2v/releases)).

The coding rules that the flow enforces mechanically are these. Latches: Yosys's `proc_dlatch` output is tee'd into `reports/latch.rpt`, Verilator lint runs with `--Werror-LATCH` when `LINTER_ERROR_ON_LATCH` is true (default), and LibreLane 3.0.3+ adds `LINTER_ERROR_ON_MULTIDRIVEN`; the fix is a default assignment at the top of every `always @*` block ([openlane2 synthesize.py](https://github.com/efabless/openlane2/blob/main/openlane/scripts/pyosys/synthesize.py); [openlane2 verilator.py](https://github.com/efabless/openlane2/blob/main/openlane/steps/verilator.py); [LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py)). Yosys `check` (run into `pre_synth_chk.rpt` right after `proc` and again into `chk.rpt` after mapping) reports combinational loops, conflicting drivers, used-but-undriven wires and unknown `$`-cells, and `ERROR_ON_SYNTH_CHECKS` (default true) makes every such warning fatal except multiple-driver warnings on tri-state cells when `SYNTH_CHECKS_ALLOW_TRISTATE` is set ([Yosys check.cc](https://github.com/YosysHQ/yosys/blob/main/passes/cmds/check.cc); [openlane2 steps/pyosys.py](https://github.com/efabless/openlane2/blob/main/openlane/steps/pyosys.py)). Assertions and prints are stripped (`hierarchy -nokeep_prints -nokeep_asserts`, then `delete t:$print; delete t:$assert`), so nothing in `$display` or `assert` reaches silicon ([openlane2 synthesize.py](https://github.com/efabless/openlane2/blob/main/openlane/scripts/pyosys/synthesize.py)). The remaining rules are standard ASIC hygiene consistent with those checks: one clock, `always @(posedge clk)` with non-blocking assignments, combinational logic in `always @*` with blocking assignments, no `initial` blocks for register values (sky130 flops have no power-on state), no `#delay`, no tri-state inside the core (LibreLane tolerates `$tribuf` only when the PDK's `SYNTH_TRISTATE_MAP` exists), and a single reset style chosen once (Tiny Tapeout uses active-low `rst_n`; a synchronous reset maps to `dfxtp` plus muxing, an asynchronous `always @(posedge clk or negedge rst_n)` maps to `dfrtp` cells through `dfflibmap`). Signed arithmetic deserves one explicit warning because it is where AI-written datapaths break: under the Verilog LRM an expression is signed only if every operand is signed, so a single unsized constant, part-select or concatenation silently makes a multiply unsigned; for a MAC declare `input signed [N-1:0] a, b`, keep the product `signed [2N-1:0]`, and give an accumulator summing K products `2N + ceil(log2 K)` bits. Verilator's `WIDTHEXPAND`/`WIDTHTRUNC` warnings catch most of these for free ([Verilator warnings](https://veripool.org/guide/latest/warnings.html)). Beware also of memories: `memory_map` expands every `reg [7:0] mem[0:1023]` into 8,192 flip-flops, because sky130 has no synthesizable SRAM in this flow; keep arrays tiny or use a hardened macro.

The lint command LibreLane runs, verbatim, is `verilator --lint-only --Wall --Wno-DECLFILENAME --Wno-EOFNEWLINE --top-module <DESIGN_NAME> <step_dir>/_deps.vlt <blackboxes> <VERILOG_FILES> --Wno-fatal --relative-includes --Werror-LATCH -I<dir> +define+<DEFINE>`, where the generated `_deps.vlt` disables `DECLFILENAME` and `EOFNEWLINE` globally and `UNDRIVEN`/`UNUSEDSIGNAL` for each blackbox file. It extracts `design__lint_error__count`, `design__lint_warning__count`, `design__inferred_latch__count` and `design__lint_timing_construct__count`, and the checkers `ERROR_ON_LINTER_ERRORS` and `ERROR_ON_LINTER_TIMING_CONSTRUCTS` are fatal by default while `ERROR_ON_LINTER_WARNINGS` is not ([openlane2 verilator.py](https://github.com/efabless/openlane2/blob/main/openlane/steps/verilator.py); [Step config vars](https://librelane.readthedocs.io/en/latest/reference/step_config_vars.html)). Outside the flow, `verilator --lint-only -Wall -Wno-DECLFILENAME --top-module top -I./rtl rtl/*.v` with `--Wno-fatal` lists everything in one pass; treat `LATCH`, `MULTIDRIVEN`, `CASEINCOMPLETE`, `UNDRIVEN` as must-fix, `WIDTHEXPAND`/`WIDTHTRUNC` as review-each, and `UNUSEDSIGNAL` as cosmetic ([Verilator warnings](https://veripool.org/guide/latest/warnings.html)). Tiny Tapeout's template turns the linter on with `RUN_LINTER: 1` and `LINTER_INCLUDE_PDK_MODELS: 1` ([ttsky template config.json](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/src/config.json)).

Simulation uses cocotb 2.x with Icarus for RTL and gate-level regression and Verilator for lint and long randomized runs. cocotb supports Icarus 11.0+ and Verilator 5.036+; the 2.0 release (2025-09-12) was API-breaking: generator coroutines and `cocotb.fork()` are gone (`async`/`await`, `cocotb.start_soon()`), `BinaryValue` became `LogicArray` with `.to_unsigned()`/`.to_signed()`, `TestFactory` became `@cocotb.parametrize`, `Timer(0)` is rejected, `Clock(..., unit=...)` replaced `units`, and the Makefile variables were renamed `MODULE`→`COCOTB_TEST_MODULES`, `TOPLEVEL`→`COCOTB_TOPLEVEL`, `COVERAGE`→`COCOTB_USER_COVERAGE`, `RANDOM_SEED`→`COCOTB_RANDOM_SEED` ([cocotb release notes](https://docs.cocotb.org/en/stable/release_notes.html); [cocotb simulator support](https://docs.cocotb.org/en/stable/simulator_support.html)). The Python runner (`get_runner(sim).build(sources=[...], hdl_toplevel="dff", always=True); runner.test(hdl_toplevel="dff", test_module="test_dff")`, run with `SIM=icarus pytest test_dff.py`) is documented as experimental ([cocotb runner](https://docs.cocotb.org/en/stable/runner.html)). Waveforms: `make SIM=icarus WAVES=1` writes `<toplevel>.fst`; Verilator needs `EXTRA_ARGS += --trace --trace-fst --trace-structs` for `dump.fst` and `--coverage` for `coverage.dat`; Surfer reads VCD, FST and GHW ([cocotb simulator support](https://docs.cocotb.org/en/stable/simulator_support.html); [brew surfer](https://formulae.brew.sh/formula/surfer)).

The gate-level simulation recipe comes straight from Tiny Tapeout's `test/Makefile`: the same `tb.v` and `test.py`, but with `GATES=yes` the build dir becomes `sim_build/gl`, `COMPILE_ARGS` gains `-DGL_TEST -DFUNCTIONAL -DUSE_POWER_PINS -DSIM -DUNIT_DELAY=#1`, and `VERILOG_SOURCES` becomes `$(PDK_ROOT)/sky130A/libs.ref/sky130_fd_sc_hd/verilog/primitives.v`, `.../sky130_fd_sc_hd.v` and `gate_level_netlist.v` (the `.pnl.v` copied from the run). Under `` `ifdef GL_TEST `` the testbench declares `wire VPWR = 1'b1; wire VGND = 1'b0;` and connects them, because "standard cells have power ports, so the design must be powered" ([tt10 Makefile](https://github.com/TinyTapeout/tt10-verilog-template/blob/main/test/Makefile); [tt10 tb.v](https://github.com/TinyTapeout/tt10-verilog-template/blob/main/test/tb.v); [Tiny Tapeout testing](https://tinytapeout.com/hdl/testing/)). Expect `x` from un-reset flops in gate-level simulation: assert reset before the first clock edge. This functional run (`UNIT_DELAY=#1`) checks connectivity and synthesis/simulation mismatches, not timing; a true timing simulation compiles the cell models *without* `-DFUNCTIONAL` so their specify blocks are active, and adds `$sdf_annotate("final/sdf/<corner>/<design>__<corner>.sdf", tb.dut)` in the testbench with a `1ns/1ps` timescale, which Icarus supports through its SDF parser (IOPATH and INTERCONNECT) ([iverilog sdf_parse.y](https://github.com/steveicarus/iverilog/blob/master/vpi/sdf_parse.y); [WPI ECE574 notes](https://schaumont.dyn.wpi.edu/ece574f24/_sources/06designflow.rst.txt)). The OpenLane guide's tip 9 is to "simulate the final gate-level netlist with SDF annotations to get closest to silicon behavior and to help validate false paths," and it notes that "timing violations reported during simulation that STA didn't catch suggest the design may be under-constrained" ([OpenLane 2 timing closure guide](https://openlane2.readthedocs.io/en/dev/usage/timing_closure/index.html)).

Formal checks are cheap insurance at this scale. SymbiYosys with `read -formal` (which defines `FORMAL` instead of `SYNTHESIS`), a `.sby` file with `mode bmc`, a depth of a few tens of cycles and `smtbmc boolector`, will verify reset values, no-overflow invariants on a MAC, and FIFO handshake properties in minutes; guard properties with `` `ifdef FORMAL `` so synthesis never sees them ([Yosys verilog_frontend.cc](https://github.com/YosysHQ/yosys/blob/main/frontends/verilog/verilog_frontend.cc); [sby install](https://yosyshq.readthedocs.io/projects/sby/en/latest/install.html)). RTL-versus-netlist equivalence with eqy uses `[gold]`/`[gate]` sections holding Yosys scripts, `[collect]` partitions and `[strategy sby]` blocks, ends with `DONE (PASS, rc=0)` or `DONE (FAIL, rc=2)`, and leaves failing traces as `trace.vcd` ([eqy quickstart](https://github.com/YosysHQ/eqy/blob/main/docs/source/quickstart.rst)). LibreLane's `Yosys.EQY` step is explicitly experimental: "you are expected to provide your own EQY script," it preprocesses sky130 cell models with `eqy.formal_pdk_proc`, and the generated default "fails in a number of scenarios" ([LibreLane yosys.py](https://github.com/librelane/librelane/blob/main/librelane/steps/yosys.py)). For a design that only Yosys and ABC transform, gate-level simulation already covers most of what eqy would, so eqy earns its keep when you hand-edit a netlist or want independent assurance on a datapath.

The verification discipline that keeps an AI-written design honest is independence: write the Python golden model from the spec in a separate directory with no imports from the RTL tree, generate stimulus with a seeded RNG (`COCOTB_RANDOM_SEED`) so failures reproduce, score at the transaction level after the pipeline latency, include hand-computed edge vectors (zero, max, sign boundaries, overflow) that depend on neither model, and run the identical test against the gate-level netlist. Anthropic's own long-running-agent guidance adds the rule that made the biggest difference in their experiments: "It is unacceptable to remove or edit tests," enforced by file structure and permissions rather than by instruction ([Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

## Synthesis: the exact Yosys and ABC sequence, and the three knobs that matter

LibreLane does not call Yosys's generic `synth` command; it drives Yosys through the Python bindings (`pyosys`) with a hand-rolled copy of `synth` so that each stage can report and so PDK techmaps can be inserted. The invocation is `yosys -y synthesize.py -- --config-in config.json --extra-in extra.json --output <design>.nl.v`. It reads every SCL `.lib` (filtered to `SYNTH_CORNER`, with `EXTRA_EXCLUDED_CELLS` and the PDK's `SYNTH_EXCLUDED_CELL_FILE` removed) as blackboxes, writes the two-line ABC constraint file, reads the RTL, and runs `hierarchy -check -top <DESIGN_NAME> -nokeep_prints -nokeep_asserts; rename -top <DESIGN_NAME>`. Then comes the proc sequence (`proc_clean; proc_rmdead; proc_prune; proc_init; proc_arst; proc_rom; proc_mux; tee -o reports/latch.rpt proc_dlatch; proc_dff; proc_memwr; proc_clean; tee -o reports/pre_synth_chk.rpt check; opt_expr`), `flatten` if `SYNTH_HIERARCHY_MODE` is `flatten` (the default; alternatives are `deferred_flatten` and `keep`), an explicit opt loop (`opt_expr; opt_merge -nomux;` then repeat `opt_muxtree; opt_reduce; opt_merge; opt_dff; opt_clean; opt_expr` until nothing changes), `fsm`, another opt loop, `wreduce; peepopt; opt_clean`, `booth` if `SYNTH_MUL_BOOTH`, `alumacc; share` (resource sharing, `SYNTH_SHARE_RESOURCES` default true), `memory -nomap; opt_clean`, `memory_map`, `techmap`, `abc -fast`, `opt -fast`, `hierarchy -check; check; stat` ([openlane2 synthesize.py](https://github.com/efabless/openlane2/blob/main/openlane/scripts/pyosys/synthesize.py); [Yosys synth](https://yosyshq.readthedocs.io/projects/yosys/en/latest/cmd/synth.html)). After deleting `$print`/`$assert` cells and writing `pre_techmap.rpt`, the PDK maps are applied: `techmap -map $SYNTH_TRISTATE_MAP; simplemap`, the full-adder map if `SYNTH_ADDER_TYPE` is `FA`, `techmap -map $SYNTH_LATCH_MAP`, and `SYNTH_EXTRA_MAPPING_FILE`. Then `dfflibmap -liberty <lib>` maps every generic flop to a sky130 flop (`post_dff.rpt`), and ABC runs as `abc -script <STRATEGY>.abc -D <CLOCK_PERIOD×1000 ps> -constr synthesis.abc.sdc -liberty <lib>` ([openlane2 synthesize.py](https://github.com/efabless/openlane2/blob/main/openlane/scripts/pyosys/synthesize.py)). Post-processing is `setundef -zero` (`SYNTH_TIE_UNDEFINED` default `low`), `hilomap -hicell sky130_fd_sc_hd__conb_1 HI -locell sky130_fd_sc_hd__conb_1 LO`, `splitnets; opt_clean -purge` (`SYNTH_SPLITNETS` true), `insbuf -buf sky130_fd_sc_hd__buf_2 A X` (`SYNTH_DIRECT_WIRE_BUFFERING` true), `check` → `chk.rpt`, `stat -json -liberty` → `stat.json`, and `write_verilog -noattr -noexpr -nohex -nodec -defparam` plus `write_json` ([openlane2 synthesize.py](https://github.com/efabless/openlane2/blob/main/openlane/scripts/pyosys/synthesize.py); [open_pdks SCL config](https://github.com/RTimothyEdwards/open_pdks/blob/master/sky130/librelane/sky130_fd_sc_hd/config.tcl)). For sky130_fd_sc_hd the cells excluded from synthesis are `clkbuf*`, `clkinv*`, `clkdlybuf*`, `dlygate*`, `dlymetal*`, `tap*`, `decap*`, `fill*`, `diode*`, `lpflow_*`, `macro_sparecell` and `probe*`, so synthesis never uses clock buffers or delay cells; those are reserved for CTS and the hold-fixing resizer ([open_pdks SCL config](https://github.com/RTimothyEdwards/open_pdks/blob/master/sky130/librelane/sky130_fd_sc_hd/config.tcl)).

A faithful standalone script, if you want to run synthesis by hand outside the flow, is the composition of the commands above:

```tcl
read_liberty -lib -ignore_miss_dir -setattr blackbox $PDK_ROOT/sky130A/libs.ref/sky130_fd_sc_hd/lib/sky130_fd_sc_hd__tt_025C_1v80.lib
read_verilog -sv -noautowire top.v
hierarchy -check -top top
synth -top top -flatten
dfflibmap -liberty $LIB
abc -D 10000 -liberty $LIB        ;# 10000 ps = 10 ns period
setundef -zero
hilomap -hicell sky130_fd_sc_hd__conb_1 HI -locell sky130_fd_sc_hd__conb_1 LO
splitnets; opt_clean -purge
check -mapped
stat -liberty $LIB
write_verilog -noattr -noexpr -nohex -nodec top.nl.v
write_json top.json
```

The ABC script is generated per strategy. The building blocks are `resyn2 = balance; drw -l; drf -l; balance; drw -l; drw -l -z; balance; drf -l -z; drw -l -z; balance`, `choice`/`choice2` (fraig_store/restore wrappers around resyn2), `map_old_dly = map -p -B 0.2 -A 0.9 -M 0` for delay, `map_new_area = amap -m -Q 0.1 -F 20 -A 20 -C 5000` for area, `retime {D} -M 5` (area) or `-M 6` (delay), and an optional `fine_tune` of `buffer -N <MAX_FANOUT_CONSTRAINT>; upsize {D}; dnsize {D}` when `SYNTH_ABC_BUFFERING` or `SYNTH_SIZING` is on. `AREA 3` is the ORFS area script (`strash; dch; map -B 0.9; topo; stime -c; buffer -c -N …; upsize -c; dnsize -c`) and `DELAY 4` is the ORFS delay script (`&get -n; &st; &dch; &nf;` then five rounds of `&st; &syn2; &if -g -K 6; &synch2; &nf`). Every script ends with `stime -p; print_stats -m` ([openlane2 construct_abc_script.py](https://github.com/efabless/openlane2/blob/main/openlane/scripts/pyosys/construct_abc_script.py)). The variable doc is honest about the choice: "AREA strategies usually result in a more compact design, while DELAY strategies usually result in a design that runs at a higher frequency. Please note that there is no way to know which strategy is the best before trying them" ([openlane2 steps/pyosys.py](https://github.com/efabless/openlane2/blob/main/openlane/steps/pyosys.py)). LibreLane ships a `SynthesisExploration` flow for exactly this sweep ([Flows reference](https://librelane.readthedocs.io/en/latest/reference/flows.html)).

The only quantitative public evidence of how much these knobs move a sky130 arithmetic path comes from a 1,440-run OpenLane 1 grid search (not peer reviewed; preprint July 2026) over `CLOCK_PERIOD` 4–10 ns, `FP_CORE_UTIL` 35–55 %, `PL_TARGET_DENSITY` 0.4–0.6 and `SYNTH_STRATEGY` 0–3. On a 4×4 array of 8-bit signed MACs with 32-bit accumulators (~11,695 cells), no configuration closed 4 ns; the best post-SPEF WNS was **−1.20 ns with Strategy 3 at 35 % utilization and 0.6 density**, implying fmax ≈ 192 MHz at the nominal corner, and "Strategy 3 improves best WNS by 2.4 ns over Strategy 0" at the cost of 59 % more cells (18,559). PicoRV32 (~10,063 cells, ~5.3 ns critical path) closed between 200 and 222 MHz only with Strategy 3; a 32-bit serial-parallel multiplier closed every frequency from 100 to 250 MHz provided density ≥ 0.5. The authors' recommendation for the MAC array is architectural: "pipeline register insertion between the multiply and accumulate stages" ([preprints.org paper](https://www.preprints.org/frontend/manuscript/bb3f29f28a8f6c2645e902cb192138d6/download_pub); [IEEE DataPort dataset](https://ieee-dataport.org/documents/openlane-sky130a-parameter-sweep-dataset-1440-run-rtl-gdsii-timing-area-and-power-results)). The practical ordering for an agent is therefore: run `AREA 0`, read `stat.rpt` area and `STAPrePNR` worst slack, try `DELAY 1` then `DELAY 4` if timing fails and `AREA 3` if area is the binding constraint, and consider `SYNTH_ADDER_TYPE: CSA` or `SYNTH_MUL_BOOTH: true` on multiplier-heavy paths. `SYNTH_ABC_BUFFERING` and `SYNTH_SIZING` are off by default because OpenROAD's resizer will redo buffering and sizing later with real parasitics.

The other synthesis knobs with defaults: `SYNTH_HIERARCHY_MODE` `flatten` (use `deferred_flatten` for per-module stats, `keep` only for macro hardening; with macros, hierarchy-preserving synthesis is "currently unsupported"), `SYNTH_ABC_DFF` false (passes flops through ABC to merge duplicates), `SYNTH_ELABORATE_ONLY` false (for structural netlists), `SYNTH_AUTONAME` false, `SYNTH_WRITE_NOATTR` true, `SYNTH_KEEP_HIERARCHY_MIN_COST`/`_INSTANCES`/`_MODULES` (LibreLane additions implemented as `keep_hierarchy -min_cost N`), `SYNTH_CLOCKGATE_MIN_WIDTH` with `SYNTH_CLOCKGATE_POSEDGE_ICG` in `<cell>/<ce>/<clk>/<gclk>` form (replacing the old Lighter plugin), and `YOSYS_LOG_LEVEL` ([LibreLane pyosys.py](https://github.com/librelane/librelane/blob/main/librelane/steps/pyosys.py); [Using Macros](https://librelane.readthedocs.io/en/latest/usage/using_macros.html)). The failure modes an agent will see map one-to-one onto the reports: "`<name>` is not declared" is `-noautowire`; "multiple conflicting drivers" in `pre_synth_chk.rpt` is two always blocks or an `assign` plus an `always` on one signal; a non-empty `latch.rpt` is an incomplete `if`/`case`; `design__instance_unmapped__count > 0` means a `$`-cell survived (`$dlatch`, `$tribuf`, `$mem`, `$lut`); "found and reported N problems" from `hierarchy -check` is a missing module in `VERILOG_FILES`; and a cell count roughly half your estimate means Yosys optimized away logic that does not reach an output, which Tiny Tapeout specifically warns about ([TT HDL Important](https://tinytapeout.com/hdl/important/)).

## Constraints: four numbers build the SDC and two of them are placeholders

Every timing decision downstream is anchored in the SDC, and LibreLane will generate one for you from `base.sdc` whenever `PNR_SDC_FILE` and `SIGNOFF_SDC_FILE` are unset (the `OpenROAD.CheckSDCFiles` step warns that the fallback is in use). The file creates one clock on the first `CLOCK_PORT` with `create_clock … -period $CLOCK_PERIOD` (warning "Multi-clock files are not currently supported by the base SDC file. Only the first clock will be constrained," and using a dummy `__VIRTUAL_CLK__` if there is no port); sets `set_input_delay` on all non-clock inputs and `set_output_delay` on all outputs to `CLOCK_PERIOD × IO_DELAY_CONSTRAINT / 100`; applies `set_max_fanout MAX_FANOUT_CONSTRAINT`, `set_max_transition` and `set_max_capacitance` if set; models external drivers with `set_driving_cell` from `SYNTH_DRIVING_CELL` (and `SYNTH_CLK_DRIVING_CELL` on the clock pin) and external loads with `set_load OUTPUT_CAP_LOAD/1000` (fF → pF); then `set_clock_uncertainty CLOCK_UNCERTAINTY_CONSTRAINT`, `set_clock_transition CLOCK_TRANSITION_CONSTRAINT`, `set_timing_derate -early (1 − TIME_DERATING_CONSTRAINT/100)` and `-late (1 + …)`, and finally `set_propagated_clock [all_clocks]` unless the step exposes `OPENLANE_SDC_IDEAL_CLOCKS`, in which case clocks are ideal ([openlane2 base.sdc](https://github.com/efabless/openlane2/blob/main/openlane/scripts/base.sdc); [LibreLane base.sdc](https://github.com/librelane/librelane/blob/main/librelane/scripts/base.sdc)). The reset-exclusion lines are commented out, so `rst_n` gets the same I/O delay as any other input.

The numbers that feed it for sky130_fd_sc_hd are: `CLOCK_PERIOD` default **10.0 ns**; `IO_DELAY_CONSTRAINT` **20 %**; `CLOCK_UNCERTAINTY_CONSTRAINT` **0.25 ns**; `CLOCK_TRANSITION_CONSTRAINT` **0.15 ns**; `TIME_DERATING_CONSTRAINT` **5 %**; `MAX_FANOUT_CONSTRAINT` **10** cells; `MAX_TRANSITION_CONSTRAINT` **0.75 ns**; `MAX_CAPACITANCE_CONSTRAINT` **0.2 pF**; `OUTPUT_CAP_LOAD` **33.442 fF**; `SYNTH_DRIVING_CELL` `sky130_fd_sc_hd__inv_2/Y`; `SYNTH_CLK_DRIVING_CELL` `sky130_fd_sc_hd__clkinv_2/Y` ([pdk_compat.py](https://github.com/librelane/librelane/blob/main/librelane/config/pdk_compat.py); [open_pdks SCL config](https://github.com/RTimothyEdwards/open_pdks/blob/master/sky130/librelane/sky130_fd_sc_hd/config.tcl); [config/flow.py](https://github.com/librelane/librelane/blob/main/librelane/config/flow.py)). With defaults, therefore, a 10 ns design has 2 ns of input delay and 2 ns of output delay reserved at the boundary, 0.25 ns subtracted from every setup check *and* charged against every hold check (because `set_clock_uncertainty` is applied without `-setup`/`-hold`), late paths multiplied by 1.05 and early paths by 0.95.

The two judgment calls here are the clock period and the I/O budget. For period, the public reference points on sky130hd are ORFS's SDC files: `gcd` at 1.1 ns, `aes` at 3.6 ns, `riscv32i` at 6.0 ns and `ibex` at 8.0 ns, all with 20 % I/O delay and a virtual clock for I/O paths ([ORFS gcd SDC](https://github.com/The-OpenROAD-Project/OpenROAD-flow-scripts/blob/master/flow/designs/sky130hd/gcd/constraint.sdc); [ORFS ibex SDC](https://github.com/The-OpenROAD-Project/OpenROAD-flow-scripts/blob/master/flow/designs/sky130hd/ibex/constraint.sdc)). Tiny Tapeout's pad (`sky130_ef_io_gpiov2_pad`) is rated for a 66 MHz input and the template sets `CLOCK_PERIOD: 20` with the comment "Increase this in case you are getting setup time violations" ([Tiny Tapeout clock spec](https://www.tinytapeout.com/specs/clock/); [ttsky template config.json](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/src/config.json)). So a small student block starts at 10 ns standalone or 20 ns on Tiny Tapeout, and tightens only if `STAPrePNR` shows large positive slack; constraining tighter than you will ever clock costs area and runtime for nothing. The 20 % I/O delay is "a placeholder budget, not a physical measurement"; for in-to-reg and reg-to-out paths you either replace it with the real external timing, or declare those paths false or multicycle. The OpenLane guide puts it bluntly: "it is your responsibility to complete the constraints by providing an SDC file custom constraints," and "OpenLane assumes a single clock domain. Multi-domain designs require you to adjust constraints and flow components yourself" ([OpenLane 2 timing closure guide](https://openlane2.readthedocs.io/en/dev/usage/timing_closure/index.html)). A custom SDC starts from `base.sdc` and adds `set_false_path -from [get_ports rst_n]` (otherwise an asynchronous reset tree is timed as a 2–4 ns-delayed input into every `dfrtp` reset pin and generates spurious recovery/removal violations), `set_multicycle_path N -setup -from … -to …` (OpenSTA semantics: "setup is checked after N cycles and hold after N−1"), and `set_clock_groups -asynchronous` for any second clock; you then point both `PNR_SDC_FILE` and `SIGNOFF_SDC_FILE` at it ([OpenSTA Sdc.tcl](https://github.com/parallaxsw/OpenSTA/blob/master/sdc/Sdc.tcl); [OpenLane 2 timing closure guide](https://openlane2.readthedocs.io/en/dev/usage/timing_closure/index.html)).

## Static timing analysis: equations, nine corners, reports, and your decisions

The setup and hold checks in their conventional form, with LibreLane's sky130 defaults substituted, are: setup slack = `(T_clk + L_capture − t_setup_lib − 0.25 ns) − 1.05 × (L_launch + t_clk→q + Σ t_logic+wire)`, and hold slack = `0.95 × (L_launch + t_clk→q + Σ t_logic+wire) − (L_capture + t_hold_lib + 0.25 ns)`, where `L` are the clock-network latencies (zero and identical before CTS because the clock is ideal; real after CTS because `set_propagated_clock` is applied). The OpenLane guide writes the same thing for a worked example as `AAT_latest = t_ck + t_CQ + t_and + t_inv + t_xor`, `RAT_s = t_ck + t_skew − t_s`, `SLACK_s = RAT_s − AAT_latest > 0` for setup and `AAT_earliest − (t_skew + t_h) > 0` for hold, states that violating either "can make a flip-flop metastable," and enumerates the four path classes in-to-out, in-to-reg, reg-to-out and reg-to-reg ([OpenLane 2 timing closure guide](https://openlane2.readthedocs.io/en/dev/usage/timing_closure/index.html)). OpenSTA's definitions are precise: `report_wns` reports "the worst negative slack. If the worst slack is positive, zero is reported," `report_tns` the total negative slack, `report_worst_slack` the raw worst slack; LibreLane stores both as `timing__setup__wns = min(0, ws)` and `timing__setup__ws` ([OpenSTA Search.tcl](https://github.com/parallaxsw/OpenSTA/blob/master/search/Search.tcl); [openlane2 corner.tcl](https://github.com/efabless/openlane2/blob/main/openlane/scripts/openroad/sta/corner.tcl)). Derating is OCV margin: `set_timing_derate -early|-late [-clock] [-data] [-cell_delay] [-net_delay] derate` ("If the -early and -late flags are omitted the both min and max paths are derated"); uncertainty is "the uncertainty or jitter in a clock"; `set_clock_transition` describes "expected transition times of the clock tree when analyzing a design using ideal clocks" ([OpenSTA Sdc.tcl](https://github.com/parallaxsw/OpenSTA/blob/master/sdc/Sdc.tcl)).

The Elmore-delay intuition you already have maps directly onto what the tool does: a cell's delay is interpolated from its Liberty NLDM table indexed by input slew and output load, and the wire between cells is modeled either as a per-unit-length RC estimate on a Steiner tree (`estimate_parasitics -placement`), as the global-route guides (`-global_routing`), or as the extracted SPEF after detailed routing. Concrete sky130_fd_sc_hd numbers from the Liberty files give you the scale. A minimum inverter `inv_1` (area 3.7536 µm², input cap 2.3 fF, max load 0.181 pF) at tt_025C_1v80 and a load of 9.52 fF (roughly FO4) has `cell_fall` 0.0455/0.0616/0.0873 ns and `cell_rise` 0.0728/0.0903/0.1211 ns for input slews of 0.01/0.053/0.122 ns, so FO4 at tt is on the order of 75–105 ps; at ss_100C_1v60 the same cell is roughly 1.5–2× slower (`cell_rise` 0.0982/0.1806 ns at 4.7/14.3 fF loads) ([inv_1 tt lib](https://github.com/google/skywater-pdk-libs-sky130_fd_sc_hd/blob/main/cells/inv/sky130_fd_sc_hd__inv_1__tt_025C_1v80.lib.json); [inv_1 ss lib](https://github.com/google/skywater-pdk-libs-sky130_fd_sc_hd/blob/main/cells/inv/sky130_fd_sc_hd__inv_1__ss_100C_1v60.lib.json)). The workhorse flop `dfxtp_1` (area 20.0192 µm²) has clk-to-Q of **0.269–0.422 ns** at tt across loads 0.5–23.6 fF (0.01 ns clock slew), setup of 0.0508 ns (rise) / 0.1033 ns (fall) at fast slews, hold of **−0.0285/−0.0468 ns** (negative, i.e. the data may change slightly before the edge), and minimum pulse widths of 0.169/0.208 ns; at ss_100C_1v60 clk-to-Q becomes **0.566–0.973 ns**, setup 0.1228/0.2602 ns, hold −0.0676/−0.0969 ns ([dfxtp_1 tt lib](https://github.com/google/skywater-pdk-libs-sky130_fd_sc_hd/blob/main/cells/dfxtp/sky130_fd_sc_hd__dfxtp_1__tt_025C_1v80.lib.json); [dfxtp_1 ss lib](https://github.com/google/skywater-pdk-libs-sky130_fd_sc_hd/blob/main/cells/dfxtp/sky130_fd_sc_hd__dfxtp_1__ss_100C_1v60.lib.json)). The per-stage sequencing overhead at tt is thus ≈ 0.30 ns clk-to-q + 0.05–0.10 ns setup + 0.25 ns uncertainty ≈ 0.6–0.65 ns, leaving about 9.3 ns of logic in a 10 ns cycle and about 19.3 ns in Tiny Tapeout's 20 ns, which is why TT designs rarely need pipelining while a 4 ns target on a MAC does.

Corners are where the engineer's first real decision sits. sky130_fd_sc_hd ships 16 PVT Liberty corners (`tt_025C_1v80`, `tt_100C_1v80`, `ss_100C_1v60`, `ss_n40C_1v28`…`1v76`, `ff_n40C_1v95`, `ff_100C_1v65`, etc.), and LibreLane's sky130 `STA_CORNERS` is the 3×3 product of interconnect corners `nom`/`min`/`max` (three OpenRCX rule sets, `rules.openrcx.sky130A.{nom,min,max}.calibre`) with `tt_025C_1v80`, `ss_100C_1v60` and `ff_n40C_1v95`, nine IPVT corners in all, with `DEFAULT_CORNER = nom_tt_025C_1v80` ([sky130_fd_sc_hd timing directory](https://foss-eda-tools.googlesource.com/skywater-pdk/libs/sky130_fd_sc_hd/+/28c101fc5db17bb6cadefa4c2a146693c685f1dc/timing); [open_pdks sky130 config.tcl](https://github.com/RTimothyEdwards/open_pdks/blob/master/sky130/librelane/config.tcl)). The "I" matters only after routing: before there is a SPEF the three interconnect variants of a PVT corner load identical files and the multi-corner STA step skips duplicates ("identical to … at this stage"), so only `STAPostPNR` really has nine distinct analyses ([openlane2 steps/openroad.py](https://github.com/efabless/openlane2/blob/main/openlane/steps/openroad.py)). Note that `ss_100C_1v60` is a 1.6 V corner, so LibreLane's default slow corner already includes an 11 % supply droop. The convention, which the Skill-Lync primer states and every interviewer expects, is that setup is signed off at the slow/hot/low-voltage corner and hold at the fast/cold/high-voltage one; in LibreLane terms `max_ss_100C_1v60` binds setup and `min_ff_n40C_1v95` binds hold ([Skill-Lync STA corners](https://resources.skill-lync.com/branches/electronics-communication/questions/vlsi-design/sta-corners-modes)). The flow enforces this differently depending on version: OpenLane 2's pdk-compat layer set `TIMING_VIOLATION_CORNERS = ["*tt*"]` so only typical-corner violations failed the run, whereas the current open_pdks sky130 config for LibreLane sets `TIMING_VIOLATION_CORNERS = "*"` and LibreLane 3.0 changed `HOLD_VIOLATION_CORNERS` to `['*']`, so hold violations on *any* of the nine corners (and setup on all of them) now fail the flow, while `MaxSlew`/`MaxCap` checkers default to matching no corners and only report ([pdk_compat.py (OpenLane 2)](https://github.com/efabless/openlane2/blob/main/openlane/config/pdk_compat.py); [open_pdks sky130 config.tcl](https://github.com/RTimothyEdwards/open_pdks/blob/master/sky130/librelane/config.tcl); [checker.py](https://github.com/librelane/librelane/blob/main/librelane/steps/checker.py); [Changelog 3.0.0](https://github.com/librelane/librelane/blob/main/Changelog.md)). Whatever the default, the sign-off definition you should state and encode is: post-RCX `STAPostPNR` with `timing__setup__ws ≥ 0` at `max_ss_100C_1v60`, `timing__hold__ws ≥ 0` at `min_ff_n40C_1v95`, zero violations at all nine, with the 0.25 ns uncertainty and ±5 % derate still applied, zero unconstrained endpoints, and `timing__unannotated_net_filtered__count = 0`.

Reading a report is a learned skill, and LibreLane's `corner.tcl` makes the report set deterministic. For each corner it runs `report_checks -sort_by_slack -path_delay max -fields {slew cap input nets fanout} -format full_clock_expanded -group_count 1000` into `max.rpt` and the `min` version into `min.rpt`; `checks.rpt` holds `report_checks -unconstrained`, `report_checks -slack_max -0.01`, `report_check_types -max_slew -max_capacitance -max_fanout -violators`, `report_parasitic_annotation -report_unannotated`, and `check_setup -verbose -unconstrained_endpoints -multiple_clock -no_clock -no_input_delay -loops -generated_clocks`; `violator_list.rpt` lists every violating endpoint as `[hold reg-reg] <start> -> <end> : <slack>` using `find_timing_paths -unique_paths_to_endpoint`; `clock.rpt` prints each clock's sources, period, whether it is propagated, `report_clock_properties`, `report_clock_latency` and `report_clock_min_period`; `skew.max/min.rpt` come from `report_clock_skew -setup|-hold` ("the maximum difference in clock arrival between every source and target register that has a path between" them) ([openlane2 corner.tcl](https://github.com/efabless/openlane2/blob/main/openlane/scripts/openroad/sta/corner.tcl); [OpenSTA Search.tcl](https://github.com/parallaxsw/OpenSTA/blob/master/search/Search.tcl)). A path in `max.rpt` has a header (Startpoint, Endpoint, Path Group, Path Type max/min, Corner), a data-arrival block starting at the launch edge with `clock network delay (propagated)` or `(ideal)` and one line per pin with Fanout, Cap, Slew, Delay and cumulative Time, a data-required block with the capture edge at `CLOCK_PERIOD`, its network delay, `clock uncertainty` (−0.25 for setup), `library setup time`, and finally `slack (MET)` or `slack (VIOLATED)`; "slack is required time minus arrival time" ([OpenLane 2 timing closure guide](https://openlane2.readthedocs.io/en/dev/usage/timing_closure/index.html)). The classic false pass is a missing clock: `timing__setup_vio__count = 0` with a huge positive worst slack, every flop listed under `check_setup`'s "no clock" output and paths in the `unconstrained` group. Always cross-check `clock.rpt` (right period, `Propagated: yes` after CTS) and `unpropagated.rpt` (must be empty after CTS).

Hold violations appear only after CTS, and understanding why is a reliable interview question. "Right after synthesis, the clock is ideal, so hold violations usually won't appear, though setup violations may," and "hold violations mainly come from clock skew" ([OpenLane 2 timing closure guide](https://openlane2.readthedocs.io/en/dev/usage/timing_closure/index.html)). The flow makes this explicit: `repair_design.tcl` runs `unset_propagated_clock [all_clocks]` before `estimate_parasitics -placement`, and `cts.tcl` runs `set_propagated_clock [all_clocks]` immediately after `clock_tree_synthesis` ([repair_design.tcl](https://github.com/efabless/openlane2/blob/main/openlane/scripts/openroad/repair_design.tcl); [cts.tcl](https://github.com/efabless/openlane2/blob/main/openlane/scripts/openroad/cts.tcl)). The mechanism is arithmetic: a direct Q→D path has arrival ≈ 0.27–0.35 ns (clk-to-q at tt), while the hold requirement is `(L_capture − L_launch) + t_hold + 0.25 ns`; a capture clock arriving 0.1 ns later than the launch clock, plus the 0.95 early derate, is enough to go negative. The binding corner is usually `min_ff_n40C_1v95` (fastest gates, least wire RC). The fix is delay insertion, and a buffer sized for ff adds roughly twice its delay at ss, which is exactly how hold fixing consumes setup slack. OpenROAD's resizer therefore orders the work: "Setup repair is done before hold repair so that hold repair does not cause setup checks to fail," and "buffers are not inserted that will cause setup violations unless `-allow_setup_violations` is specified" ([OpenROAD rsz README](https://github.com/The-OpenROAD-Project/OpenROAD/blob/master/src/rsz/README.md)). LibreLane's variable doc for `PL_RESIZER_ALLOW_SETUP_VIOS` explains the asymmetry every engineer should be able to recite: "Setup violations are less dangerous as they simply mean a chip may not run at its rated speed, however, chips with hold violations are essentially dead-on-arrival" ([openlane2 steps/openroad.py](https://github.com/efabless/openlane2/blob/main/openlane/steps/openroad.py)).

The resizer runs four times with a deliberate margin schedule. `RepairDesignPostGPL` runs `repair_design -verbose -max_wire_length $DESIGN_REPAIR_MAX_WIRE_LENGTH -slew_margin 20 -cap_margin 20` after `buffer_ports -inputs`/`-outputs` and with ideal clocks; it "inserts buffers on nets to repair max slew, max capacitance and max fanout violations, and on long wires to reduce RC delay… It also resizes gates to normalize slews," using a default limit of 50 load pins when neither Liberty nor SDC constrains fanout; "placement-based parasitics cannot accurately predict routed parasitics, so a margin can be used to 'over-repair'" ([OpenROAD rsz README](https://github.com/The-OpenROAD-Project/OpenROAD/blob/master/src/rsz/README.md); [repair_design.tcl](https://github.com/efabless/openlane2/blob/main/openlane/scripts/openroad/repair_design.tcl)). `ResizerTimingPostCTS` runs `repair_timing -setup -setup_margin 0.05 -max_buffer_percent 50` then `repair_timing -hold -setup_margin 0.05 -hold_margin 0.1 -max_buffer_percent 50` with propagated clocks and placement parasitics; the post-GRT pass (off by default in 3.0 as experimental) uses `-global_routing` parasitics and the tighter 0.025/0.05 ns margins; the post-GRT `repair_design` uses 10 % margins. The setup move sequence is `unbuffer vt_swap sizeup swap buffer clone split` across phases `LEGACY LAST_GASP CRIT_VT_SWAP`, i.e. gate sizing, pin swapping, rebuffering, load splitting, cloning, buffer removal and buffer-to-inverter replacement, and OpenROAD's own `-max_buffer_percent` default of 20 is raised to 50 by LibreLane ([rsz_timing_postcts.tcl](https://github.com/efabless/openlane2/blob/main/openlane/scripts/openroad/rsz_timing_postcts.tcl); [OpenROAD rsz README](https://github.com/The-OpenROAD-Project/OpenROAD/blob/master/src/rsz/README.md); [LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py)). Tiny Tapeout's template restates the two hold margins with the comment "Increase them in case you are getting hold violations" ([tt10 config.json](https://github.com/TinyTapeout/tt10-verilog-template/blob/main/src/config.json)). Protect hand-built structures from the resizer with `RSZ_DONT_TOUCH_RX` (a regex, default `$^`) or `RSZ_DONT_TOUCH_LIST`.

What you decide, ordered from free to expensive, is a decision tree you should be able to recite. First, constraint sanity: confirm the clock in `clock.rpt`, check `checks.rpt` for `check_setup` warnings and unconstrained endpoints, and replace the 20 % placeholder I/O delays or add false/multicycle paths for reset, configuration and debug paths; a large share of setup violations on small designs are in-to-reg or reg-to-out paths timed against a fictitious I/O delay. Second, read the worst path in `max.rpt` at the worst corner and classify it: long logic depth (an RTL or synthesis problem), one net with huge fanout or slow slew (a DRV problem for the resizer), clock-network-delay dominated (a CTS problem), or I/O-dominated (a constraint problem); check which `[setup reg-reg|in-reg|reg-out]` kind dominates `violator_list.rpt`. Third, synthesis strategy (`DELAY 0..4`, `SYNTH_ADDER_TYPE CSA/FA`, `SYNTH_SIZING`) which the grid search showed can move an arithmetic path by over 2 ns at 20–60 % area cost. Fourth, utilization and density (`FP_CORE_UTIL` 50 → 35–40, `PL_TARGET_DENSITY_PCT`) to give the resizer room and shorten wires. Fifth, resizer settings: raise `PL_RESIZER_SETUP_SLACK_MARGIN`/`GRT_RESIZER_SETUP_SLACK_MARGIN` to leave post-route headroom, raise `*_MAX_BUFFER_PCT` (and the guide's tip 6: "If you raise them, lower FP_CORE_UTIL to avoid congestion"), enable `DESIGN_REPAIR_REMOVE_BUFFERS` to let the resizer rebuild Yosys's buffer trees. Sixth, CTS: restrict `CTS_CLK_BUFFERS` to smaller drives, shrink `CTS_SINK_CLUSTERING_MAX_DIAMETER`/`SIZE`, lower `CTS_MAX_SLEW` ("consider limiting clock buffer sizes with CTS_CLK_BUFFERS"). Seventh, hold strategy: keep the 0.1/0.05 ns over-fix margins, and if hold fixing destroys setup prefer reducing skew over `*_ALLOW_SETUP_VIOS`, which is only acceptable when the chip will be clocked slower than `CLOCK_PERIOD` anyway (tip 4). Eighth, relax the clock if frequency is negotiable (remembering that `MAX_TRANSITION_CONSTRAINT` defaults to 10 % of the period capped by `DEFAULT_MAX_TRAN`, and I/O delays scale with it). Ninth and last, go back to RTL: pipeline between multiply and accumulate, retime, reduce fanout of control signals, replace ripple adders with CLA/CSA or carry-save accumulators ([OpenLane 2 timing closure guide](https://openlane2.readthedocs.io/en/dev/usage/timing_closure/index.html); [preprints.org paper](https://www.preprints.org/frontend/manuscript/bb3f29f28a8f6c2645e902cb192138d6/download_pub)). Tip 10 closes the loop: "Max capacitance and max transition violations are acceptable if there are no setup or hold violations, but they are useful indicators of design issues."

## Place and route: how the five OpenROAD engines work and where the tradeoffs sit

Floorplanning is either relative or absolute. With `FP_SIZING: relative` (default) the die is derived from `FP_CORE_UTIL` (default **50 %**; the Caravel guide says "Typical values … range from 25% to 60%. 40% is a good starting value"), `FP_ASPECT_RATIO` (1), and the margins `BOTTOM/TOP_MARGIN_MULT` = 4 site heights and `LEFT/RIGHT_MARGIN_MULT` = 12 site widths; with `absolute`, you give `DIE_AREA` as "x0 y0 x1 y1" in µm (and optionally `CORE_AREA`, which must be paired with it) and utilization becomes an output rather than an input, which is the Tiny Tapeout case ([LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py); [Caravel macro-first guide](https://librelane.readthedocs.io/en/latest/additional_material/caravel/macro_first_hardening/index.html); [openlane2 openroad.py](https://raw.githubusercontent.com/efabless/openlane2/main/openlane/steps/openroad.py)). The placement site for sky130_fd_sc_hd is `unithd`; tap cells (`sky130_fd_sc_hd__tapvpwrvgnd_1`) are inserted every `FP_TAPCELL_DIST` = **13 µm** and end caps are `decap_3` ([open_pdks SCL config](https://github.com/RTimothyEdwards/open_pdks/blob/master/sky130/librelane/sky130_fd_sc_hd/config.tcl); [open_pdks sky130 config.tcl](https://github.com/RTimothyEdwards/open_pdks/blob/master/sky130/librelane/config.tcl)). The physics: tap cells tie n-well to VDD and substrate to GND at a bounded pitch so the parasitic PNPN thyristor between adjacent wells never turns on (latch-up); end caps terminate rows so well and implant edges meet DRC; decaps are MOS capacitors that supply local charge during switching. The industry rule of thumb for tap pitch is ≤ 20–30 µm ([SemiMatrix floorplanning](https://semimatrix.onrender.com/topic/topic-floorplan.html)). Pins are placed by OpenROAD's `place_pins` in `IO_PIN_PLACEMENT_MODE` `matching` (default), `random_equidistant` or `annealing`, on `IO_PIN_H_LAYER` met3 and `IO_PIN_V_LAYER` met2 for sky130, or from a pin-order file (`IO_PIN_ORDER_CFG`, with `#N/#S/#E/#W` sections, regex lines and `@min_distance` annotations) or a template DEF (`FP_DEF_TEMPLATE`, `FP_TEMPLATE_MATCH_MODE strict`) ([LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py); [Pin placer config](https://librelane.readthedocs.io/en/latest/reference/pin_placement_cfg.html)).

The power distribution network is built by OpenROAD `pdngen`: `add_pdn_stripe -followpins` creates the met1 rails that follow the standard-cell rows, `add_pdn_stripe -layer -width -pitch -offset -spacing` adds straps, `add_pdn_ring` an optional core ring, and `add_pdn_connect -layers` the via stacks wherever power nets overlap across layers; `pdngen -skip_trim` keeps metal stubs, `-failed_via_report` lists vias that could not be made, and `repair_pdn_vias` removes PDN vias that cause DRC after routing ([OpenROAD pdn README](https://openroad.readthedocs.io/en/latest/main/src/pdn/README.html)). For sky130A the PDK sets `PDN_RAIL_LAYER met1` (`PDN_RAIL_WIDTH 0.48`), `PDN_VERTICAL_LAYER met4`, `PDN_HORIZONTAL_LAYER met5`, strap widths **1.6 µm**, spacing 1.7 µm, `PDN_VPITCH 153.6`, `PDN_HPITCH 153.18`, offsets 16.32/16.65 µm, and core-ring widths 1.6/spacing 1.7/offset 6 ([open_pdks sky130 config.tcl](https://github.com/RTimothyEdwards/open_pdks/blob/master/sky130/librelane/config.tcl)). Because pitch and offset are absolute microns, a die smaller than one pitch plus offset gets zero straps on that layer, which is the classic floating-rail failure on small macros and the reason `PDN_MULTILAYER: false` exists ("uses only the lower layer"); Tiny Tapeout sets it, together with `RT_MAX_LAYER: met4` and `FP_PDN_VPITCH: 38.87`, because the tile is supplied from the parent on met4 and met5 is reserved ([ttsky template config.json](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/src/config.json); [Caravel macro-first guide](https://librelane.readthedocs.io/en/latest/additional_material/caravel/macro_first_hardening/index.html)). `Checker.PowerGridViolations` fails on `check_power_grid` errors but its doc says "you may ignore these if LVS passes" ([checker.py](https://github.com/librelane/librelane/blob/main/librelane/steps/checker.py)). The industry framing is that a frontside PDN consumes 25–35 % of frontside routing resources and is sized for ≤ 3–5 % static IR drop; too dense blocks signals, too sparse fails IR and EM ([SemiMatrix floorplanning](https://semimatrix.onrender.com/topic/topic-floorplan.html)).

Global placement is RePlAce, "an analytic, nonlinear placer that solves electrostatic force equations using Nesterov's method." Cells are modeled as electric charges, their density as a charge distribution whose potential is computed by FFT in O(n log n), and the gradient of that potential is an electric field that pushes overlapping cells apart; the objective is `f(v) = W(v) + λ·D(v)`, where `W` is half-perimeter wirelength smoothed with weighted-average smoothing and `D` is the density cost, minimized with Nesterov's accelerated gradient while the penalty `λ` is ramped by a factor `cof` chosen to keep the per-iteration HPWL change within [0.95, 1.05]. "Overflow" is the fraction of total cell area sitting in over-full bins (0 ≤ τ ≤ 1), and placement terminates when it drops below `-overflow` (default **0.1**); an initial BiCGSTAB solve "improves HPWL by about 5% on large designs," divergence is caught by snapshot-and-revert, and results are deterministic across platforms ([OpenROAD gpl README](https://openroad.readthedocs.io/en/latest/main/src/gpl/README.html); [RePlAce paper](https://vlsicad.ucsd.edu/Publications/Journals/j126.pdf)). Timing-driven mode (`-timing_driven`) "runs a virtual repair_design to find slacks, then weights the nets with the lowest slack," applying `-timing_driven_net_weight_max` 5 in full to the worst 0.2 % of nets and re-weighting at overflow thresholds [64, 20]; routability-driven mode runs RUDY each iteration and inflates cells in congested tiles (coefficient 2, max ratio 3, max density 0.99), stopping when the congestion metric fails to improve three times. The RePlAce paper reports 2 % average HPWL reduction on ISPD-2005/2006 and 8.5–9.6 % scaled-HPWL on DAC/ICCAD-2012 versus other academic placers ([OpenROAD gpl README](https://openroad.readthedocs.io/en/latest/main/src/gpl/README.html); [RePlAce paper](https://vlsicad.ucsd.edu/Publications/Journals/j126.pdf)). LibreLane's defaults are `PL_TARGET_DENSITY_PCT = FP_CORE_UTIL + 5×GPL_CELL_PADDING + 10` (so 60 % for 50 % utilization on sky130_fd_sc_hd, whose `GPL_CELL_PADDING` is 0), `PL_TIMING_DRIVEN` **false** in 3.0 (it was true in OpenLane 2), `PL_ROUTABILITY_DRIVEN` true, `PL_WIRE_LENGTH_COEF` 0.25, and `PL_MIN/MAX_PHI_COEFFICIENT` "useful if global placement diverges" ([LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py); [Step config vars](https://librelane.readthedocs.io/en/latest/reference/step_config_vars.html)). The tradeoff: target density must exceed utilization or the placer cannot spread cells; set near 100 % it degenerates to pure wirelength minimization with heavy overlap handed to the legalizer; set near utilization it converges slowly or diverges. Tiny Tapeout's template uses 60 % and notes that "users have reported that values up to 80 worked well" when `GPL-0302` fails ([ttsky template config.json](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/src/config.json)).

Legalization (OpenDP, `detailed_placement`) moves cells to legal row sites with minimum displacement; the default NegotiationLegalizer is "a two-pass legalizer based on the NBLG paper… slightly slower but handles dense designs," versus the legacy diamond-search BFS that "cannot handle dense designs." LibreLane bounds displacement at `PL_MAX_DISPLACEMENT_X` **500 µm** and `_Y` **100 µm**, runs `optimize_mirroring`, and applies `DPL_CELL_PADDING` (0 on sky130); `check_placement` returns 0 when legal ([OpenROAD dpl README](https://openroad.readthedocs.io/en/latest/main/src/dpl/README.html); [LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py)).

Clock tree synthesis is TritonCTS 2.0 with on-the-fly buffer characterization. The sequence LibreLane runs is `repair_clock_inverters; configure_cts_characterization [-max_cap CTS_MAX_CAP] [-max_slew CTS_MAX_SLEW]; clock_tree_synthesis -buf_list $CTS_CLK_BUFFERS -root_buf $CTS_ROOT_BUFFER -sink_clustering_size 25 -sink_clustering_max_diameter 50 -sink_clustering_enable; set_propagated_clock [all_clocks]; estimate_parasitics -placement; repair_clock_nets -max_wire_length $CTS_CLK_MAX_WIRE_LENGTH;` legalize; `report_cts` ([cts.tcl](https://github.com/efabless/openlane2/blob/main/openlane/scripts/openroad/cts.tcl)). Sink clustering uses CKMeans (exponent 4, unbalance ratio 0.6) and "adds one sub-tree level before the H-tree: each cluster is driven by buffer which becomes end point of H-tree structure"; `-apply_ndr half` (the default) applies a 2× spacing non-default rule to clock nets except leaf nets; `-sink_buffer_max_cap_derate` 0.01 favors strong buffers; `report_cts` gives the number of clock roots, buffers inserted, subnets and sinks, while skew and latency come from STA ([OpenROAD cts README](https://openroad.readthedocs.io/en/latest/main/src/cts/README.html)). For sky130 the root buffer is `clkbuf_16` and the buffer list is `clkbuf_*`; `clkbuf_16` has 7.4 fF input cap, 1.53 pF max load, and `cell_rise` of 0.093–0.18 ns across 0.5–105 fF loads at tt, so for a design of hundreds to a few thousand flops expect a root plus one clustered level, insertion latency of a few hundred picoseconds and skew of tens to ~100–200 ps at tt; read the real numbers in `skew.max.rpt` and `clock.rpt` ([open_pdks SCL config](https://github.com/RTimothyEdwards/open_pdks/blob/master/sky130/librelane/sky130_fd_sc_hd/config.tcl); [clkbuf_16 tt lib](https://github.com/google/skywater-pdk-libs-sky130_fd_sc_hd/blob/main/cells/clkbuf/sky130_fd_sc_hd__clkbuf_16__tt_025C_1v80.lib.json)). The tradeoff on clustering: a larger cluster size or diameter means fewer buffers and less clock power but more local skew and leaf-net capacitance; smaller means tighter skew at more area and power. The industry nuance an interviewer may probe is that skew targets should be derived from hold margins (maximum allowed skew on a hold-critical path = CK-Q + net delay − hold time), that over-tight targets raise latency, OCV sensitivity and power, and that jitter belongs in the clock period rather than in uncertainty so that multicycle paths scale ([eeNews margins](https://www.eenewseurope.com/en/deriving-design-margins-for-successful-timing-closure/)). Useful skew and concurrent clock-datapath optimization are things CCOpt does and TritonCTS does not; its nearest knobs (`-balance_levels`, `-insertion_delay`, `-delay_buffer_derate`) balance macro-versus-register latency.

Global routing is FastRoute 4.1 lineage: nets become Steiner trees (Prim-Dijkstra) over a GCell grid whose default cell is 15 M3 pitches, with up to `-congestion_iterations` 50 rip-up-and-reroute passes to eliminate overflow (demand minus capacity on a GCell edge, a different quantity from placement overflow). Capacity is deliberately derated by `set_global_routing_layer_adjustment` ("reduces routing resources by a percentage… Negative values increase capacity"), which LibreLane sets globally with `GRT_ADJUSTMENT` **0.3** plus the PDK's per-layer `GRT_LAYER_ADJUSTMENTS = "0.99,0,0,0,0,0"` (li1 almost fully blocked), within `RT_MIN_LAYER met1`–`RT_MAX_LAYER met5` and clock nets no lower than met3 ([OpenROAD grt README](https://openroad.readthedocs.io/en/latest/main/src/grt/README.html); [open_pdks sky130 config.tcl](https://github.com/RTimothyEdwards/open_pdks/blob/master/sky130/librelane/config.tcl)). With `GRT_ALLOW_CONGESTION` false, remaining overflow fails the step; Tiny Tapeout sets it to 1 and lets the detailed router try. The congestion-fixing ladder, cheapest first, is: lower `PL_TARGET_DENSITY_PCT` or add `GPL_CELL_PADDING`, enlarge the die or lower `FP_CORE_UTIL`, open layers or reduce adjustment on uncongested ones, add `ROUTING_OBSTRUCTIONS`/halos where PDN or macro pins block tracks, and only then `GRT_ALLOW_CONGESTION`, which usually trades overflow for DRC.

Detailed routing is TritonRoute: pin-access analysis, track assignment, initial routing, then "search and repair" iterations with an integrated DRC engine, run by LibreLane with `DRT_OPT_ITERS` **64** (OpenROAD's maximum) and `DRT_THREADS` equal to the machine's thread count; since 3.0 DRT-level antenna repair is on by default (`DRT_ANTENNA_REPAIR_ITERS` 3, margin 10 %) and `Checker.TrDRC` fails on any remaining `route__drc_errors` ([OpenROAD drt README](https://openroad.readthedocs.io/en/latest/main/src/drt/README.html); [LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py)). A healthy log shows violations falling by orders of magnitude in the first ten iterations and reaching zero well before 64; a plateau at a non-zero count is structural (a cell with no pin access, a PDN via overlapping a pin, an off-grid pin from a template, or congestion inherited from `-allow_congestion`), and more iterations will not fix it. `report_wire_length`, `report_net_detours` and `Checker.WireLength` (PDK `WIRE_LENGTH_THRESHOLD`) flag the long-wire symptoms.

The antenna effect is a manufacturing rule, not a timing one: during plasma etch a long floating wire connected only to a gate collects charge, and the gate oxide is the only discharge path. SkyWater's rule limits "the maximum allowed ratio of interconnect area exposed to plasma etch to active gate poly area," counting bottom areas of licon/mcon/via/via2 and perimeter areas of poly/li/met1–met3; a reverse-biased diffusion diode on the net discharges it and reduces the effective ratio, and the antenna devices do not appear in LVS ([SkyWater antenna rules](https://skywater-pdk.readthedocs.io/en/main/_sources/rules/antenna.rst.txt)). OpenROAD's checker computes a partial area ratio per wire and a cumulative ratio per gate-wire pair against the LEF `AntennaRule`; the fixes are diode insertion (`repair_antennas [diode] -iterations -ratio_margin`, which needs fillers removed first and warns `GRT-0243` if the technology's side-area ratios are constant rather than piecewise-linear) and, in commercial routers, layer-hopping jumpers that connect the gate through the top layer last, which OpenROAD does not implement as a command ([OpenROAD ant README](https://openroad.readthedocs.io/en/latest/main/src/ant/README.html); [OpenROAD grt README](https://openroad.readthedocs.io/en/latest/main/src/grt/README.html)). The antenna checker "runs thrice during the flow: once immediately after global routing, once as part of OpenROAD.RepairAntennas, during signoff," using `sky130_fd_sc_hd__diode_2/DIODE` on sky130; `DIODE_ON_PORTS` and `RUN_HEURISTIC_DIODE_INSERTION` (threshold 90 µm, off by default) are the OpenLane-1-compatible alternatives ([Newcomers' Tutorial](https://librelane.readthedocs.io/en/latest/getting_started/newcomers/index.html); [LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py)).

Fill and extraction close out the physical work. `filler_placement` "fills gaps between placed instances to connect power and ground rails" using the PDK's `FILL_CELLS` (`fill*`) and `DECAP_CELLS` (`decap*`); metal density rules (sky130 `m1.pd.*`, up to 0.77 maximum metal1 density over 50 µm windows and min-area rules such as `m1.6` 0.083 µm² and `m5.4` 4.0 µm²) exist for CMP and etch uniformity, and metal fill for the top level is added by the integrator rather than the user project ([OpenROAD dpl README](https://openroad.readthedocs.io/en/latest/main/src/dpl/README.html); [SkyWater periphery rules](https://skywater-pdk.readthedocs.io/en/main/rules/periphery.html)). OpenRCX then "extracts resistance and capacitance from routed designs in the LEF/DEF layout model" by interpolating per-corner rule files generated once per node from characterized wire patterns, with `-coupling_threshold` 0.1 fF below which coupling is grounded and `RCX_MERGE_VIA_WIRE_RES` true; LibreLane writes one SPEF per corner into `NN-openroad-rcx/<corner>/` ([OpenROAD rcx README](https://openroad.readthedocs.io/en/latest/main/src/rcx/README.html); [openlane2 steps/openroad.py](https://github.com/efabless/openlane2/blob/main/openlane/steps/openroad.py)). The accuracy hierarchy the flow follows is `set_wire_rc` layer-average estimates (placement stage) < global-route guides (post-GRT) < OpenRCX SPEF (signoff); `STAPostPNR` runs `report_parasitic_annotation -report_unannotated` and `filter_unannotated.py` to produce `timing__unannotated_net_filtered__count`, which must be zero for a trustworthy report ([filter_unannotated.py](https://github.com/efabless/openlane2/blob/main/openlane/scripts/odbpy/filter_unannotated.py)). IR drop is OpenROAD `psm` (PDNSim): `analyze_power_grid -net VPWR` solves the resistive PDN with per-instance currents from OpenSTA's `report_power` (vectorless unless you read a VCD/SAIF), reports worst drop and per-segment current with `-enable_em`, checks for floating stripes, and `insert_decap` targets the highest-drop regions; LibreLane's `IRDropReport` writes `ir__drop__avg`, `ir__drop__worst` and `ir__voltage__worst` ([OpenROAD psm README](https://openroad.readthedocs.io/en/latest/main/src/psm/README.html); [LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py)). No published sky130 or Tiny Tapeout IR budget exists; the industry rule of 3–5 % of VDD is ~90 mV at 1.8 V.

## Signoff: two DRC decks, Netgen LVS, XOR, and the checklist that means tapeout-ready

Physical signoff in this flow is deliberately redundant. Magic streams the DEF to GDS (`Magic.StreamOut`, `MAGIC_GDS_MERGE` true, `MAGIC_DEF_LABELS` false in 3.0, "disable if LVS fails"), KLayout independently streams the same DEF (`KLayout.StreamOut` with the PDK's `.lyt/.lyp/.map`), and `KLayout.XOR` compares the two GDS files ignoring sky130 layer `81/14`; `design__xor_difference__count` must be zero ([LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py); [open_pdks sky130 config.tcl](https://github.com/RTimothyEdwards/open_pdks/blob/master/sky130/librelane/config.tcl)). Two DRC decks then run on the GDS: Magic's (`MAGIC_DRC_USE_GDS` true, `MAGIC_GDS_FLATGLOB` "to prevent false positive DRC errors") and KLayout's `sky130A_mr.drc` runset with `KLAYOUT_DRC_DEFINES` (`beol 1 feol 1 floating_metal 0 seal 1 offgrid 1`), each with its own `ERROR_ON_*` checker ([Step config vars](https://librelane.readthedocs.io/en/latest/reference/step_config_vars.html)). The rule IDs in the reports are SkyWater's (`m1.1` width 0.14 µm, `m1.2` spacing 0.14, `li.6` area 0.0561 µm², `poly.1a` width 0.15, `nwell.1` width 0.84, `m5.1`/`m5.2` 1.6 µm), so the fix reads directly from the rule table: widen, space, enclose, add area ([SkyWater periphery rules](https://skywater-pdk.readthedocs.io/en/main/rules/periphery.html)). Common causes in a flow-generated layout are PDN straps landing on pins, pins too close or below min-area (`IO_PIN_MIN_DISTANCE`, derived `IO_PIN_V/H_LENGTH`), off-grid shapes from a template or manual placement, and residual detailed-route violations.

LVS is Magic extraction followed by Netgen. `Magic.SpiceExtraction` extracts from DEF/LEF by default (`MAGIC_EXT_USE_GDS` false is faster), with `MAGIC_EXT_UNIQUE all`, optional `MAGIC_EXT_SHORT_RESISTOR` to localize shorts and `MAGIC_EXT_ABSTRACT_CELLS` to black-box macros consistently; `Checker.IllegalOverlap` fails on `magic__illegal_overlap__count`. `Netgen.LVS` compares the extracted SPICE against the powered netlist (`pnl`) with the PDK's `NETGEN_SETUP` (`sky130A_setup.tcl`), and the metrics `design__lvs_error__count`, `design__lvs_device/net_difference__count`, `design__lvs_unmatched_device/net/pin__count` and `design__lvs_property_fail__count` all must be zero; the log must end "Final result: Circuits match uniquely." ([LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py); [Newcomers' Tutorial](https://librelane.readthedocs.io/en/latest/getting_started/newcomers/index.html)). The canonical Magic/Netgen sequence by hand is `extract`, `ext2spice lvs`, `ext2spice`, then `lvs {layout.spice top} {schematic.spice top} setup.tcl out.log`, with the warning that equation-defined MOSFET parameters in a schematic can make Netgen segfault and that residual property mismatches (`m=2` vs `nf=2`) can be benign ([laygo2 sky130 LVS example](https://laygo2-sky130-docs.readthedocs.io/en/main/example_lvs.html)). Typical failure causes are mis-named or missing power pins (`VDD_PIN`/`GND_PIN`, `FP_TEMPLATE_COPY_POWER_PINS`), nets shorted by strap overlaps, floating nets (`report_floating_nets`), macros black-boxed on one side only, and tap/fill cells present in layout but handled by the Netgen setup.

The LibreLane checker list is the operational definition of "clean," and every item is a metric you can assert on: `design__lint_error__count = 0`, `synthesis__check_error__count = 0`, `design__instance_unmapped__count = 0`, no `assign` statements in the netlist, `design__power_grid_violation__count` (ignorable if LVS passes), `design__critical_disconnected_pin__count = 0`, `route__wirelength__max` under threshold, `route__drc_errors = 0`, `antenna__violating__pins` reviewed, `timing__setup_vio__count = timing__hold_vio__count = 0` across the configured corners, `design__max_slew/cap_violation__count` reviewed, `design__xor_difference__count = 0`, `magic__drc_error__count = 0`, `klayout__drc_error__count = 0`, `magic__illegal_overlap__count = 0`, `design__lvs_error__count = 0`, and finally `Misc.ReportManufacturability` summarizing DRC, LVS and antenna ([LibreLane classic.py table](https://github.com/librelane/librelane/blob/main/librelane/flows/classic.py); [Step config vars](https://librelane.readthedocs.io/en/latest/reference/step_config_vars.html)). To that the integrator adds structural checks (Tiny Tapeout's boundary, pins, power pins, layers and cell names; Caravel's consistency and XOR-outside-user-area), and you add the gate-level simulation with the final `.pnl.v` and, ideally, an SDF-annotated run at the ss corner. The ordered list a student should be able to recite, with tool and pass criterion, is: RTL lint and synthesis checks clean (Verilator/Yosys); PDN sane (`check_power_grid`); placement legal (`check_placement` = 0); CTS done, skew and latency reviewed (OpenSTA); global route with zero overflow; detailed route with zero DRC; antenna clean; fill inserted; SPEF per corner and nine-corner STA with no setup/hold/cap/slew violations; IR drop reviewed; GDS streamed and XOR clean; Magic and KLayout DRC zero; Netgen LVS match; integrator checks; gate-level simulation passes. Where the OpenLane 2 defaults differ from LibreLane 3.0, the 3.0 behaviour is stricter (hold on all corners, DRT antenna repair on) and that is the version Tiny Tapeout runs.

## Tiny Tapeout, October 2026: TTSKY26d closes 2026-11-30 and these are the rules

Three shuttles are open as of 2026-10-21: **TTSKY26d** (sky130, launched 2026-09-22, closes **2026-11-30**, ChipFoundry shuttle CI-2612, chips expected 2027-05-12, shipping est. 2027-06-09), **TTGF26c** (GF180MCU via wafer.space, closes 2026-12-07) and TTGF26d (same run, reserved for a museum, unused tiles released two days before the deadline). The next IHP shuttle (TTIHP27a) is projected for March 2027 and the next sky130 after 26d for May 2027; sky130 and GF shuttles run roughly every 2–3 months, IHP about twice a year, and the historical gap from close to chips-in-hand is 6–13 months ([Tiny Tapeout chips page](https://tinytapeout.com/chips/); [Tiny Tapeout FAQ](https://tinytapeout.com/faq/)). Sky130 shuttles now run through ChipFoundry, founded by the Efabless founders after Efabless closed in March 2025 (which cancelled TT10 and delayed TT08/09); the only public price anchor is Matt Venn's May 2025 estimate of "likely €300 for a devkit and €70 per tile," and current prices live only in the calculator at app.tinytapeout.com ([eeNews Europe](https://www.eenewseurope.com/en/tiny-tapeout-sees-industrial-boost-as-it-recovers-from-efabless-closure/); [Tiny Tapeout homepage](https://tinytapeout.com/)). You receive a devkit (chip on a removable breakout board plus the RP2350 "ETR" demo board); bare chips are not sold ([Tiny Tapeout FAQ](https://tinytapeout.com/faq/); [TT PCB ETR](https://tinytapeout.com/specs/pcb-etr/)).

Start from the per-PDK template, `TinyTapeout/ttsky-verilog-template` for sky130 (the old `tt10-verilog-template` belongs to the cancelled TT10). Required files are `info.yaml` (`yaml_version: 6`), `src/project.v` and `src/config.json`, `docs/info.md`, `test/{Makefile,tb.v,test.py,requirements.txt}` and four workflows `gds`, `test`, `docs`, `fpga` ([TT HDL templates](https://tinytapeout.com/hdl/templates/); [ttsky-verilog-template](https://github.com/TinyTapeout/ttsky-verilog-template)). The top module must be named `tt_um_<something>` (include your GitHub username) and must have exactly these ports and no others:

```verilog
`default_nettype none
module tt_um_example (
    input  wire [7:0] ui_in,    // Dedicated inputs
    output wire [7:0] uo_out,   // Dedicated outputs
    input  wire [7:0] uio_in,   // IOs: Input path
    output wire [7:0] uio_out,  // IOs: Output path
    output wire [7:0] uio_oe,   // IOs: Enable path (active high: 0=input, 1=output)
    input  wire       ena,      // always 1 when the design is powered, so you can ignore it
    input  wire       clk,      // clock
    input  wire       rst_n     // reset_n - low to reset
);
  assign uo_out  = ui_in + uio_in;   // All output pins must be assigned. If not used, assign to 0.
  assign uio_out = 0;
  assign uio_oe  = 0;
  wire _unused = &{ena, clk, rst_n, 1'b0};
endmodule
```

The tool's `check_ports()` requires each port with exact direction and width and errors "module has unsupported extra ports" otherwise; tristate is only available through `uio_oe`, so your RTL never drives `'z` ([ttsky template project.v](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/src/project.v); [tt-support-tools project.py](https://github.com/TinyTapeout/tt-support-tools/blob/main/project.py)). `info.yaml` holds `project:` with `title`, `author`, `discord`, `description`, `language`, `clock_hz`, `tiles` (sky/IHP valid values `1x1, 1x2, 2x2, 3x2, 4x2, 6x2, 8x2`), `top_module`, and `source_files` (every file listed, all in `./src`; "Don't forget to also update PROJECT_SOURCES in test/Makefile"), followed by `pinout:` with exactly 24 keys `ui[0..7]`, `uo[0..7]`, `uio[0..7]` ("DO NOT delete or add any pins") ([ttsky template info.yaml](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/info.yaml)). `docs/info.md` must contain "How it works", "How to test" and "External hardware," with images under 512 kB each and 1 MB total, and feeds the Typst datasheet built by `tt_tool.py --check-docs` and `--create-pdf` ([ttsky template docs/info.md](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/docs/info.md); [tt-gds-action docs](https://github.com/TinyTapeout/tt-gds-action/blob/ttsky26d/docs/action.yml)).

Tile geometry is exact. sky130A `DIE_AREA` values from `tile_sizes.yaml` are **1x1 161.00×111.52 µm**, 1x2 161.00×225.76, 2x2 334.88×225.76, 3x2 508.76×225.76, 4x2 682.64×225.76, 6x2 1030.40×225.76, 8x2 1378.16×225.76 (plus 3x4, 4x4, 5x4, 6x4 and 8x4 that the template does not accept); IHP 1x1 is 202.08×154.98 and GF180 1x1 is 346.64×160.72 ([tile_sizes.yaml](https://github.com/TinyTapeout/tt-support-tools/blob/main/tech/sky130A/tile_sizes.yaml)). A tile "fits roughly 1000 digital logic gates depending on gate size," and the tool warns if a project synthesizes to fewer than 20 cells ([Tiny Tapeout FAQ](https://tinytapeout.com/faq/); [tt-support-tools project.py](https://github.com/TinyTapeout/tt-support-tools/blob/main/project.py)). Set `tiles: "1x2"` and run the action to find out whether a bigger design fits before buying ([Tiny Tapeout FAQ](https://tinytapeout.com/faq/)). The flow fixes the floorplan: `tt_tool.py --create-user-config` writes `src/user_config.json` with `DESIGN_NAME`, `VERILOG_FILES`, `DIE_AREA` from the yaml, `FP_DEF_TEMPLATE = ../tt/tech/sky130A/def/tt_block_<tiles>_<suffix>.def` (pin positions), `VDD_PIN: VPWR`, `GND_PIN: VGND`, `RT_MAX_LAYER: met4`, merges it with `src/config.json` into `src/config_merged.json`, and hardens with `python -m librelane --dockerized --docker-no-tty --pdk-root "$PDK_ROOT" --run-tag wokwi --force-run-dir runs/wokwi src/config_merged.json` ([tt-support-tools project.py](https://github.com/TinyTapeout/tt-support-tools/blob/main/project.py)). The template's `src/config.json` (header: "DO NOT EDIT THIS FILE unless you know what you are doing") sets `PL_TARGET_DENSITY_PCT: 60`, `CLOCK_PERIOD: 20`, `CLOCK_PORT: "clk"`, `PL_RESIZER_HOLD_SLACK_MARGIN: 0.1`, `GRT_RESIZER_HOLD_SLACK_MARGIN: 0.05`, `DESIGN_REPAIR_BUFFER_OUTPUT_PORTS: 0` ("Don't put clock buffers on the outputs"), `FP_SIZING: absolute`, `GRT_ALLOW_CONGESTION: 1`, `RUN_CTS: 1`, `RT_MAX_LAYER: met4`, `FP_PDN_MULTILAYER: 0`, `FP_PDN_VPITCH: 38.87`, `RUN_KLAYOUT_XOR: 0`, `RUN_KLAYOUT_DRC: 0`, `MAGIC_DEF_LABELS: 0`, `MAGIC_WRITE_LEF_PINONLY: 1`, `RUN_LINTER: 1`, `LINTER_INCLUDE_PDK_MODELS: 1` ([ttsky template config.json](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/src/config.json); [tt10 config.json](https://github.com/TinyTapeout/tt10-verilog-template/blob/main/src/config.json)). Note that KLayout DRC and XOR are disabled in the user's harden for speed; precheck runs them later. Clocking: the pad is rated 66 MHz in and 33 MHz out, inputs are not 5 V tolerant, drive is 4 mA, there is "up to 10 nanoseconds" of insertion delay between the pad and your project's clock and ~20 ns worst-case round-trip I/O latency, and the demo board generates 1 Hz–66.5 MHz; so an accelerator should treat the external interface as ~25–30 MHz and keep anything faster internal ([Tiny Tapeout clock spec](https://www.tinytapeout.com/specs/clock/); [Tiny Tapeout GPIO spec](https://tinytapeout.com/specs/gpio/)).

To harden locally with bit-identical results to CI: Python 3.11+, Docker running, on macOS `brew install libpng qhull cairo`; `git clone https://github.com/TinyTapeout/tt-support-tools tt` inside the project; a venv; `pip install -r tt/requirements.txt`; `export PDK_ROOT=~/ttsetup/pdk PDK=sky130A LIBRELANE_TAG=3.0.14`; `pip install librelane==$LIBRELANE_TAG`; `ciel enable --pdk-family sky130 8afc8346a57fe1ab7934ba5a6056ea8b43078e71`; then `./tt/tt_tool.py --create-user-config`, `./tt/tt_tool.py --harden`, `./tt/tt_tool.py --print-warnings` (synthesis and clock warnings), `--print-stats` (utilization from `GPL-0019`), `--print-cell-category`, `--open-in-openroad`, `--open-in-klayout`, and `--create-png` (needs `librsvg2-bin` and `pngquant`). The website's guide still says 3.0.3 but tells you to read the `librelane-version` default in `tt-gds-action`'s `action.yml`, which is **3.0.14** on `main` and the `ttsky26d` tag; the whole local process "should take roughly 10 minutes" ([TT local hardening](https://www.tinytapeout.com/guides/local-hardening); [tt-gds-action action.yml](https://github.com/TinyTapeout/tt-gds-action/blob/main/action.yml)). The gate-level netlist lands at `runs/wokwi/final/pnl/<top>.pnl.v`; copy it to `test/gate_level_netlist.v` and run `make -B GATES=yes` ([ttsky template test/README.md](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/test/README.md)). The template's `test.py` uses `Clock(dut.clk, 10, unit="us")`, holds `rst_n` low for 10 cycles and asserts `uo_out == 50`; CI's `test.yaml` runs on ubuntu-24.04 with apt `iverilog`, then `python -m cocotb_tools.check_results results.xml` because "make returns success even if tests fail" (both are cocotb 2.x APIs) ([ttsky template test.py](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/test/test.py); [ttsky template test.yaml](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/.github/workflows/test.yaml)).

The GDS workflow pins `TinyTapeout/tt-gds-action@ttsky26d` with `pdk: sky130A` and runs four jobs, `gds`, `precheck`, `gl_test` and `viewer`. The action installs the pinned PDK via `ciel-action`, runs `--create-user-config`, `--harden`, summarizes the Verilator lint log, `--print-warnings`, `--print-stats`, `--print-cell-category`, uploads `GDS_logs`, runs `--create-tt-submission` and uploads the `tt_submission` artifact (src, docs, GDS/LEF/netlist/`pdk.json`, `info.yaml`, `LICENSE`), then renders `gds_render.png` ([ttsky template gds.yaml](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/.github/workflows/gds.yaml); [tt-gds-action action.yml](https://raw.githubusercontent.com/TinyTapeout/tt-gds-action/ttsky26d/action.yml)). Precheck downloads that artifact and runs `precheck.py --gds <file> --tech sky130A` in a Nix shell with **KLayout 0.30.4 and Magic 8.3.568**. For sky130A it runs, in order: Magic DRC (`magic_drc.tcl` with the PDK `.magicrc`); KLayout `sky130A_mr.drc` three times (`feol`, `beol`, `offgrid`); `pin_label_purposes_overlapping_drawing`; `zeroarea`; "KLayout Checks" (top cell name equals `top_module`, no forbidden layers, i.e. no `met5.drawing/pin/label`, prBoundary present); pin check against the template DEF (messages such as "Wrong die origin in LEF, expecting (0, 0)", "Inconsistent die area between LEF and template DEF", "Unexpected port layer in LEF", "Some ports are missing or have wrong dimensions"); boundary check (top-cell bbox "must be exactly (0,0) to (die_width, die_height)", nothing outside); power-pin check (Verilog and LEF must contain `VGND` and `VDPWR`, which is VPWR renamed, with `USE POWER`/`USE GROUND` in the LEF, power pins on met4 with width ≥ 1.2 µm); layer check (every GDS layer/datatype in `valid_layers`); cell-name check (no `#` or `/`); nwell/urpm; analog-pin check if applicable; Verilog syntax via `yowasp-yosys read_verilog -sv`. "Every check runs and failures are collected" into `reports/results.md`; there is no LVS, density or antenna check for sky130 in precheck (LVS runs inside LibreLane; GF180 gets an explicit antenna deck) ([tt-support-tools precheck.py](https://github.com/TinyTapeout/tt-support-tools/blob/main/precheck/precheck.py); [pin_check.py](https://github.com/TinyTapeout/tt-support-tools/blob/main/precheck/pin_check.py); [tech_data.py](https://github.com/TinyTapeout/tt-support-tools/blob/main/precheck/tech_data.py); [tt-gds-action precheck](https://github.com/TinyTapeout/tt-gds-action/blob/ttsky26d/precheck/action.yml)). `gl_test` installs TinyTapeout's Icarus 13.0 `.deb`, copies `tt_submission/*.v` to `test/gate_level_netlist.v`, runs `GATES=yes make`, and fails on any `<failure|error>` in `results.xml`; `viewer` publishes `tinytapeout.oas` to GitHub Pages for the 3D viewer, which is why the README tells you to enable Pages ([tt-gds-action gl_test](https://github.com/TinyTapeout/tt-gds-action/blob/ttsky26d/gl_test/action.yml); [viewer action](https://github.com/TinyTapeout/tt-gds-action/blob/ttsky26d/viewer/action.yml)). For a pure digital design precheck failures are rare because the template DEF guarantees pins; they come from editing `config.json` below the "do not change" line, hand-placed layers, or an empty or misnamed top cell. Projects whose GDS action fails cannot be submitted ([Tiny Tapeout FAQ](https://tinytapeout.com/faq/)).

Submission itself is a web flow: once `gds` and `docs` are green, sign in with GitHub at app.tinytapeout.com/projects/create, "Create a new project," paste the repo URL, pay or enter a coupon, and press **"Submit a new revision"**; the project is not on the tapeout until that button is pressed, and you can resubmit revisions until the shuttle closes ([Advanced workshop: submit](https://tinytapeout.com/guides/advanced-workshop/submit-your-design/); [Tiny Tapeout FAQ](https://tinytapeout.com/faq/)). After fabrication, flash the SDK v3 UF2 to the RP2350 board, then `tt.shuttle.tt_um_<name>.enable()`, `tt.clock_project_PWM(freq_hz)` (or `clock_project_once()`), `tt.reset_project(True/False)`, write `tt.ui_in.value`, read `tt.uo_out.value`, and use `tt.uio_in/uio_out` with `RPMode.ASIC_RP_CONTROL`; the same byte-level protocol you wrote for cocotb can be replayed on silicon from MicroPython ([tt-micropython-firmware](https://github.com/TinyTapeout/tt-micropython-firmware)). An iCE40 UP5K "FPGA ASIC simulator" breakout exists for pre-silicon board-level validation via the `fpga` workflow (disabled by default with `branches: none`) and `tt_fpga.py harden` ([TT FPGA breakout guide](https://tinytapeout.com/guides/fpga-breakout/); [ttsky template fpga.yaml](https://raw.githubusercontent.com/TinyTapeout/ttsky-verilog-template/main/.github/workflows/fpga.yaml)).

## Industry mapping and the interview answers the notes support

An NVIDIA new-college-grad physical design posting enumerates the job in its own words: "Run synthesis workflows and optimize for area, power, and timing," "Run physical design flow from netlist to GDS, perform STA, physical verification (LVS/DRC)," "Perform netlist checks and formal equivalence validation," with required tool experience in Synopsys "(ICC2/DC/PT/STAR/ICV)" and Cadence "(Genus/Innovus/Tempus)" and "Python, Perl, Tcl, Make scripting" desired ([NVIDIA posting](https://jobs.anitab.org/companies/nvidia/jobs/50147664-vlsi-physical-design-engineer-new-college-grad-2025)). The OpenROAD flow implements the identical stage sequence (synthesis, floorplan with tap cells and PDN, placement and legalization, resizing/buffering, CTS, timing optimization, global and detailed routing, finishing with fill, signoff timing, GDS, DRC/LVS) through modules named `ifp`, `ppl`, `mpl`, `tap`, `pdn`, `gpl`, `dpl`, `rsz`, `cts`, `grt`, `drt`, `ant`, `fin`, `rcx`, `psm`, `dft` and OpenSTA ([OpenROAD README](https://openroad.readthedocs.io/en/latest/_sources/main/README2.md); [OpenROAD docs](https://openroad.readthedocs.io/en/latest/)). The one peer-comparable data point for honesty: on IHP SG13G2 130 nm at 50 MHz with identical constraints, the open flow (Yosys+ABC, OpenLane/OpenROAD, KLayout DRC, Netgen LVS) produced a CMN core at 0.343 mm² / 15.8 mW / 7,886 cells versus Genus/Innovus/Tempus at 0.161 mm² / 4.74 mW / 5,976 cells, and an FSM with 53 % more area and 118 % more power; SDF-accurate simulation was available only on the commercial side, and DFT, MMMC, OCV and extraction accuracy were not evaluated ([arXiv 2512.06122](https://arxiv.org/pdf/2512.06122)). The honest interview line is therefore "same flow architecture and Tcl-driven scripting model, less mature optimization engines, and no signoff-grade MMMC/OCV/SI, DFT or foundry-certified physical verification."

The mapping rows combine the arXiv comparison's tool pairing, OpenROAD's module list and NVIDIA's named tools; the commercial command names are conventional usage ([arXiv 2512.06122](https://arxiv.org/pdf/2512.06122); [OpenROAD docs](https://openroad.readthedocs.io/en/latest/); [NVIDIA posting](https://jobs.anitab.org/companies/nvidia/jobs/50147664-vlsi-physical-design-engineer-new-college-grad-2025)).

What industry adds that your sky130 flow omits is the second half of the story. Signoff STA runs across many mode×corner scenarios ("Signoff may require passing 10-30+ scenarios"), with setup at slow/low-V/hot corners and hold at fast ones, plus OCV-family derates: plain OCV applies one chip-wide early/late derate, AOCV makes the derate depend on logic depth and location (deeper paths average out random variation; in TSMC's reference flow since 9.0), and POCV/SOCV is "practical SSTA" with per-cell sigma ([Skill-Lync STA corners](https://resources.skill-lync.com/branches/electronics-communication/questions/vlsi-design/sta-corners-modes); [Tech Design Forums OCV](https://www.techdesignforums.com/practice/?p=5633)). A practitioner starting point for global derates is 10 % early / 20 % late (`set_timing_derate -early 0.9 -late 1.2`), tuned down per library, which is larger than LibreLane's ±5 % ([EDAboard derating thread](https://edaboard.com/threads/how-to-decide-derating-value.313926/?amp=1)). Margins shrink through the flow by design: synthesis uncertainty = noise + OCV + skew + placement margin, placement drops the placement term, CTS drops skew, post-CTS keeps only noise, and SI signoff sets uncertainty to zero and analyzes crosstalk directly; CPPR (common-path pessimism removal) must be accounted for because launch and capture share a clock segment ([eeNews margins](https://www.eenewseurope.com/en/deriving-design-margins-for-successful-timing-closure/)). Utilization by node is 75–85 % at mature nodes, 65–72 % at FinFET 16–5 nm and ~55–62 % sub-2 nm; macros go on the periphery with pins facing the core and 3–6 µm halos; a square core minimizes wirelength and skew ([SemiMatrix floorplanning](https://semimatrix.onrender.com/topic/topic-floorplan.html)). Blocks are sized so a trial place-and-route "complete[s] in less than a day" and runs as an overnight batch job, with abstracts and timing models at the top level ([Electronic Design](https://www.electronicdesign.com/news/products/article/21789568/maximizing-hierarchical-design-throughput-for-todays-large-designs)). DFT converts every flop to a scan flop stitched into chains so ATPG patterns are shifted in, captured for one clock and shifted out on ATE; hobby shuttles skip it because there is no production test, and Tiny Tapeout's historical "scan chain" (TT02's ~500-buffer chain that "was distorting the clock pulse") was an I/O multiplexing mechanism, not test DFT ([Scan Insertion](https://rvidisharoopchand.substack.com/p/scan-insertion); [TT03 launch](https://www.tinytapeout.com/news/tt03-launch/)). Metal-only ECOs "rewire spare cells to realize incremental design changes by changing only the masks of metal layers," which is why spare cells are pre-placed ([NYCU metal-only ECO](https://ir.lib.nycu.edu.tw:443/handle/11536/14576)).

The questions that recur across campus-placement banks, with answers anchored to the numbers above, are collected in the table that follows; the bank itself covers library characterization, OCV, recovery/removal, multi-Vt, max transition/cap, halo versus blockage, decaps, fillers, spare cells, high-fanout nets, clock gating, NDR, jitter, via pillars, EM, double patterning, ERC and density ([ChipEdge top-20 PD questions](https://chipedge.com/resources/top-20-physical-design-interview-questions-for-campus-placements/)).

| Question | Answer you can give with evidence from this flow |
|---|---|
| Setup vs hold? | Setup: data stable before the capture edge; limits fmax; checked at the slow corner (`max_ss_100C_1v60`). Hold: data stable after the edge; frequency-independent; checked at the fast corner (`min_ff_n40C_1v95`). sky130 `dfxtp_1`: setup ~0.05–0.10 ns, hold slightly negative, clk-to-q ~0.27–0.42 ns at tt. |
| What happens as skew increases? | Positive skew (capture later) helps setup, hurts hold; beyond CK-Q + net delay − t_hold the path fails hold. Over-tight skew targets raise latency, OCV sensitivity and power. |
| Why do hold violations appear only after CTS? | Pre-CTS the clock is ideal (zero skew); `set_propagated_clock` after CTS exposes launch/capture latency differences; LibreLane also charges 0.25 ns uncertainty against hold. |
| How do you fix hold without breaking setup? | Run setup repair first, then hold repair that refuses buffers which would violate setup (`repair_timing -hold` without `-allow_setup_violations`); add delay only on the short path near the capture flop; re-check setup at ss. |
| OCV, AOCV, POCV? | Global early/late derates; depth- and distance-dependent derates; statistical per-cell sigma. LibreLane uses ±5 % flat. |
| CRPR/CPPR? | Removing pessimism from applying early and late derates to the clock segment common to launch and capture. |
| What does `-max_buffer_percent` protect against? | Area and congestion blow-up from hold/setup buffering; LibreLane caps at 50 % and the guide says lower `FP_CORE_UTIL` if you raise it. |
| Antenna effect and fixes? | Plasma charge collected by long floating metal damages gate oxide; fixes are antenna diodes (`repair_antennas`, `diode_2`) or layer-hopping jumpers; checked three times in the flow. |
| Latch-up and tap cells? | Parasitic PNPN between wells; taps tie wells/substrate to rails every 13 µm on sky130 (`FP_TAPCELL_DIST`), ≤ 20–30 µm in general practice. |
| IR drop? | Resistive loss in the PDN; static vs dynamic; target 3–5 % of VDD; fixed with denser straps, more vias, decaps; OpenROAD `psm` is static-only. |
| What is overflow in placement vs routing? | Placement: fraction of cell area in over-full bins, terminates at 0.1. Routing: demand minus capacity on GCell edges, removed by rip-up/reroute within 50 iterations. |
| Utilization vs target density? | Utilization is cell area / core area (floorplan); target density is the per-bin cap the placer respects and must exceed utilization (LibreLane: util + 10). |
| Congestion fixes? | Lower density/utilization, padding, blockages/halos, open layers or reduce derate, last resort allow congestion. |
| CTS goals and knobs? | Skew, latency, slew, power; clustering size/diameter, buffer list, root buffer, NDR; ICGs balanced as sinks. |
| Multicycle path? | `set_multicycle_path N`: setup checked after N cycles, hold after N−1; jitter belongs in the period so it scales. |
| False path? | A path STA should ignore (CDC, static config, reset); "identify false paths carefully, since tools will otherwise waste effort fixing them." |
| PVT corners and MMMC? | SS/TT/FF × V × T × RC corners × modes; 10–30+ scenarios in industry; LibreLane uses 9 IPVT corners. |
| Crosstalk/SI? | Coupling-induced delta delay and glitches; analyzed at signoff with uncertainty set to zero; OpenSTA has no SI. |
| Max transition/cap/fanout? | Electrical DRVs; `repair_design` fixes them with buffering and sizing; acceptable if setup/hold are clean but indicate design issues. |
| Halo vs blockage? | Halo moves with the macro; blockage is fixed in place. |
| EM? | Metal migration under high current density; wider wires, via arrays; `psm -enable_em` reports current but not limits. |
| DRC/LVS clean? | Zero violations in two independent decks (Magic, KLayout) and Netgen "Circuits match uniquely"; plus XOR of two stream-outs. |
| LEC? | Proving netlist ≡ RTL after every netlist change (Formality/Conformal); open flow has eqy, experimental. |
| Timing vs functional vs metal-only ECO? | Post-route sizing/buffering from signoff STA; RTL-driven netlist patch; rewiring spare cells with metal masks only. |
| DFT? | Scan insertion between synthesis and floorplan, chain reordering after placement, shift/capture as extra STA modes; absent in hobby flows. |

The way to tell the tapeout story is to lead with the flow in industry words ("RTL through Yosys synthesis, OpenROAD floorplan/PDN/placement/CTS/route, OpenRCX extraction, nine-corner OpenSTA, Magic and KLayout DRC, Netgen LVS, to GDS"), name the commercial equivalents, be explicit about what was missing (no DFT, no MMMC beyond nine corners, flat ±5 % derates rather than AOCV/POCV, no SI, static IR only, no LEC in the loop, no hierarchical partitioning, and the PPA gap the arXiv paper measured), and then describe one judgment call you made with a rule of thumb and how you checked it (a congestion map, a slack histogram, a DRC count).

## Automation: what Claude Code can run overnight and what still needs you

Everything from lint to precheck is a deterministic command with a machine-readable result, which is precisely the kind of work the current Claude Code primitives are built for. In headless mode `claude -p "..."` runs non-interactively; `--permission-mode` takes `default|acceptEdits|plan|auto|dontAsk|bypassPermissions`; `--allowedTools "Bash(make *),Read"` uses the permission-rule syntax where `*` matches any text including spaces and a compound command must match on every subcommand (so `Bash(make *)` does not authorize `make && rm -rf runs`); `--permission-prompts none` (v2.1.259+) is designed "when nobody is available to answer permission prompts, for example in a scheduled job": anything that would prompt is denied, `AskUserQuestion` is removed, and the run continues; `--max-turns N` and `--max-budget-usd` bound the session ("Spend can pass the cap, so leave headroom"); `--output-format stream-json --verbose` gives a log with `session_id` and `total_cost_usd` in the final `result`; `--resume <id>` continues a session; `--bare` skips project hooks/MCP discovery and is "the recommended mode for scripted and SDK calls" ([Headless](https://code.claude.com/docs/en/headless); [CLI reference](https://code.claude.com/docs/en/cli-reference); [Permissions](https://code.claude.com/docs/en/permissions)). The docs are explicit that `bypassPermissions` skips prompts even for writes to `.git` and `.claude` and should be used "only in isolated environments like containers or VMs," and, crucially, that "permission rules are enforced by Claude Code, not by the model. Instructions in your prompt or CLAUDE.md shape what Claude tries to do, but they don't change what Claude Code allows" ([Permissions](https://code.claude.com/docs/en/permissions)). `/goal <condition>` wraps a session-scoped Stop hook evaluated by a small model after each turn (Not-yet-met / Met / Impossible); it "doesn't run commands or read files independently, so write the condition as something Claude's own output can demonstrate," bound it with "or stop after N turns," and run it in auto mode to let turns proceed unattended; it survives `--resume`, pauses on rate limits, and stops if Claude stalls ([Goal](https://code.claude.com/docs/en/goal)). Hooks are the deterministic guardrail: a `PreToolUse` command hook that exits 2 blocks the tool call with its stderr fed back to Claude, a `Stop` hook returning `{"decision": "block", "reason": "..."}` "sends Claude back to keep working," and hooks are recommended "for actions that must happen every time with zero exceptions. Unlike CLAUDE.md instructions which are advisory, hooks are deterministic" ([Hooks](https://code.claude.com/docs/en/hooks); [Best practices](https://code.claude.com/docs/en/best-practices)). Subagents in `.claude/agents/*.md` get their own tools, model, `maxTurns` and hooks, with only a summary returning to the parent, which is how you get an independent reviewer "so the agent doing the work isn't the one grading it" ([Subagents](https://code.claude.com/docs/en/sub-agents); [Best practices](https://code.claude.com/docs/en/best-practices)).

The published prior art is consistent about what agents are good at here and how they fail. ORFS-agent (Claude 3.5 Sonnet, 25 parallel ORFS jobs per iteration, 30-minute timeouts) improved wirelength or effective clock period by **13.2 % on average** over default ORFS with 12 knobs, beating OR-AutoTuner on 12 of 24 metrics with 40 % fewer iterations at a total API cost of US$48, but when detailed routing timed out it "falls back to the post-CTS surrogate" ([arXiv 2506.08332](https://arxiv.org/html/2506.08332v2)). AuDoPEDA (a Codex-class agent editing OpenROAD source with a `flow`/`measure`/`rollback` toolset) cut routed wirelength by up to 5.96 % with two regressions, guarded by runtime gates that reject added DRCs or worse WNS, automatic rollback and bisect, and fast proxy flows before full signoff ([arXiv 2601.06268](https://arxiv.org/html/2601.06268v1)). In a Tiny Tapeout classroom study, 8 of 8 high-school designs written with an LLM agent passed simulation and the backend flow, but one "consistently passed simulation but contained non-synthesizable Verilog code," and when two designs exceeded one tile "the chat agent alone was insufficient for this task and instructor expertise was essential" ([arXiv 2601.13815](https://arxiv.org/pdf/2601.13815)). ChatEDA's motivation line explains the generic failure: LLMs' "limited EDA toolchain familiarity … leads to frequent tool-usage errors" ([arXiv 2308.10204](https://arxiv.org/abs/2308.10204)). An OpenROAD MCP server exists (`claude mcp add --transport stdio openroad-mcp -- uvx --from git+https://github.com/luarss/openroad-mcp openroad-mcp`) exposing interactive OpenROAD sessions and ORFS report images ([openroad-mcp](https://github.com/luarss/openroad-mcp)). Anthropic's own harness post reports agents that "tried to one-shot the whole app, ran out of context mid-implementation, and left features half-built," and later agents that "saw partial progress and declared the job done"; its remedy is an initializer that writes a feature list as JSON (chosen because the model is less likely to tamper with it than Markdown), a progress file, `init.sh`, git commits per feature, and the rule that tests are immutable ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

Translating that into a pipeline, the design that follows from the evidence is a Makefile gate ladder the agent may run but not edit, each target deterministic and loggable: `make lint` (Verilator), `make sim` (cocotb RTL against `golden/` vectors produced by `ref/model.py` in a separate session with no access to `src/`), `make synth` (Yosys; fail on latches and `$mem` inference), `make harden` (LibreLane via the Python API, with `DeferredStepError`s captured), `make gls` (`GATES=yes` with functional cell models), `make sdf` (same testbench with `$sdf_annotate`, cell models without `-DFUNCTIONAL`), `make eqy`, `make formal` (sby), and `make precheck` (tt-support-tools). The orchestrator wraps `Classic(cfg, design_dir=...).start(tag=TAG)`, reads each step's `state_out.json`, renders an image per step (OpenROAD `save_image -web -width 1024 layout.png`, which "runs entirely server-side without a display and is suitable for headless CI," with `-display_option {rudy true}` for a congestion heat map; or `klayout.lay`'s `LayoutView.save_image_with_options`; or Tiny Tapeout's gdstk `write_svg` + `rsvg-convert`), and appends `{step_id, status, metrics_delta, log_path, image_path}` to a `manifest.json` that a static dashboard reads alongside `final/metrics.json` ([OpenROAD web README](https://github.com/The-OpenROAD-Project/OpenROAD/blob/master/src/web/README.md); [LibreLane render.py](https://github.com/librelane/librelane/blob/main/librelane/scripts/klayout/render.py); [tt-support-tools render_utils.py](https://github.com/TinyTapeout/tt-support-tools/blob/main/render_utils.py)). Resumability is native on both sides: LibreLane's `--last-run --from <step>` and Claude Code's `--resume`. The permissions file that makes the rules real rather than advisory is:

```json
{"$schema": "https://json.schemastore.org/claude-code-settings.json",
 "permissions": {
   "allow": ["Bash(make *)", "Bash(git add *)", "Bash(git commit *)", "Bash(git log *)", "Bash(git diff *)", "Read"],
   "deny":  ["Edit(./tests/**)", "Write(./tests/**)", "Edit(./golden/**)", "Write(./golden/**)",
             "Edit(./ref/**)", "Edit(./.claude/**)", "Read(./.env)", "Read(./.env.*)",
             "Bash(git push *)", "Bash(rm -rf *)", "Bash(docker *)"],
   "defaultMode": "dontAsk"}}
```

with a belt-and-braces `PreToolUse` hook (`"if": "Edit(./tests/*)"`, exit 2) because deny rules apply immediately even from a committed project file while `allow` rules only apply after the folder is trusted ([Settings](https://code.claude.com/docs/en/settings); [Hooks](https://code.claude.com/docs/en/hooks)). The overnight driver is then a bounded loop:

```bash
TAG=night-$(date +%Y%m%d-%H%M); SID=$(uuidgen | tr 'A-Z' 'a-z')
caffeinate -dims bash -c "
claude -p \"/goal runs/$TAG/status.json reports all gates PASS (lint, sim, synth, harden, gls, eqy, precheck) \
  or needs_human.json lists a blocking item; or stop after 80 turns. Start by reading CLAUDE.md, progress.md \
  and git log --oneline -20. Commit after each green gate.\" \
  --session-id $SID --permission-mode dontAsk --permission-prompts none \
  --allowedTools 'Bash(make *),Bash(git add *),Bash(git commit *),Bash(git log *),Bash(git diff *),Read,Edit' \
  --max-turns 80 --max-budget-usd 25 --output-format stream-json --verbose \
  --append-system-prompt-file .claude/overnight-rules.md | tee runs/$TAG/agent/stream.jsonl"
# loop: if status.json is not terminal and budget remains, re-invoke with --resume $SID
```

Since `--max-turns` has no default and a goal can run indefinitely, the shell loop, not the agent, is the clock; every re-invocation starts from on-disk state (`progress.md`, `status.json`, git log), which is what prevents the context-collapse failure Anthropic documented. A Stop hook should refuse to end the session while any gate is red unless `needs_human.json` explains why, and the morning report (`report.md` with the gates table, metrics versus the previous tag, images, deferred errors and the `total_cost_usd` from the final JSON) should be generated deterministically by the orchestrator, with `--json-schema` forcing a `{"gates": {...}, "needs_human": [...], "next_steps": [...]}` summary from the agent ([Headless](https://code.claude.com/docs/en/headless); [CLI reference](https://code.claude.com/docs/en/cli-reference)).

The division of labour is then unambiguous. The agent can, unattended: author RTL to a spec and iterate on lint and synthesis errors; write and run cocotb tests against a reference model it did not write; sweep `SYNTH_STRATEGY`, `FP_CORE_UTIL`, `PL_TARGET_DENSITY_PCT` and `CLOCK_PERIOD` (via `config.copy()` and `start_step_async()`) and pick the winner on measured post-SPEF metrics rather than a mid-flow surrogate; classify the worst path in `max.rpt` and apply the decision tree's cheap steps (strategy, density, resizer margins, CTS buffer list); re-run `--from OpenROAD.CTS` after a change; run gate-level and SDF simulation, eqy and precheck; and produce the dashboard. The agent must not: edit tests, golden vectors or the reference model; declare success from `STAMidPNR` numbers; "fix" an eqy, LVS or DRC failure by changing the checker's script or disabling a checker (put `EQY_SCRIPT`, `RUN_*` and `ERROR_ON_*` keys under deny or a hook); or raise `*_ALLOW_SETUP_VIOS` without a human sign-off, because that converts a frequency problem into a decision about the chip's rated speed. The items that require a human, in the order you will meet them, are the spec and architecture decisions (clock target, tile count, pin map and the byte-serial protocol the 8+8+8 pins force on an accelerator), the tokens and secrets (`claude setup-token` output placed by hand; the agent never reads `.env`), any config change below Tiny Tapeout's "do not edit" line, the Tiny Tapeout account, payment, shuttle selection and the "Submit a new revision" click (tt-support-tools has no submission API), any eqy/LVS/DRC failure the agent cannot explain in one sentence, and hardware bring-up ([tt_tool.py](https://github.com/TinyTapeout/tt-support-tools/blob/main/tt_tool.py); [Headless](https://code.claude.com/docs/en/headless); [arXiv 2601.13815](https://arxiv.org/pdf/2601.13815)).

## Conclusion

The most useful thing to internalize is that the open flow is not a toy approximation of industry practice but the same sequence with the signoff layers peeled off, and that the layers it keeps are exactly the ones whose semantics you must own: a four-number SDC that is a placeholder until you replace the I/O budget and declare your false paths, a nine-corner STA whose pass/fail scope you must deliberately widen to ss-for-setup and ff-for-hold, a resizer whose margin schedule encodes the accuracy ladder from Steiner estimates to SPEF, and a hold-repair pass that will, by design, refuse to help you if you have asked for a clock you cannot have. An interviewer at NVIDIA will not care that you used TritonCTS rather than CCOpt; they will care whether you can explain why hold violations appear only after `set_propagated_clock`, why a buffer sized at ff costs twice as much at ss, why target density must exceed utilization, and what you did when the worst path in `max.rpt` turned out to be an in-to-reg path timed against a fictitious 4 ns input delay.

For the automated pipeline, the evidence from ORFS-agent, AuDoPEDA and the Tiny Tapeout classroom study points the same way as Anthropic's harness guidance: the agent is a decision-maker over a deterministic, resumable flow, not the flow itself. LibreLane already gives you the resumable state machine, the metrics dictionary and the checker semantics; Claude Code already gives you deny rules, hooks, goals and bounded headless sessions. What you add is the independence structure, a reference model and golden vectors the design agent cannot touch, a gate ladder it cannot rewrite, and a morning queue of the decisions that are genuinely yours. Build that and the question stops being whether an agent can take RTL to GDS overnight (it can, for a tile-sized design, in about ten minutes of actual tool time per iteration) and becomes how much of the design space it should be allowed to explore before you look at the slack histogram and press submit before 2026-11-30.
